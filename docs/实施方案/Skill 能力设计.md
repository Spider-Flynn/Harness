# Harness Skill 能力设计

> 状态：目标 Skill 已完成初步实现，尚未完成隔离行为验收、整体试运行或业务项目接入。

## 一、设计原则

Skill 只承载具有独立触发边界、稳定输入输出、关键执行规则和明确失败回流的能力。以下内容
不因属于某个子系统就自动创建 Skill：

- AI 根据当前项目规则即可完成的普通判断；
- 只服务全局状态、交接、失效和恢复的运行编排；
- 更适合放入用户或项目 `AGENTS.md` 的长期规则；
- 更适合由 Agent 配置、Profile、脚本、测试、Hook 或外部工具承担的能力。

系统分类、目录和 Skill 不是一一对应关系。七个主流程系统仍然成立；横向能力没有独立时序，
额外能力也不进入每次主交付链。

## 二、目标能力拓扑

| 能力目录 | Skill | 性质 | 直接职责 |
|---|---|---|---|
| `1. 意图接入系统` | `intent` | 固定门禁 | 形成当前任务唯一有效的已确认意图 |
|  | `cooper` | 条件能力 | 读取用户明确指定的 Cooper 材料 |
| `2. 知识系统` | `know` | 检索固定、沉淀条件触发 | 检索并整合任务信息元，组织知识候选、受控写入并验证 |
|  | `build` | 显式建设路由 | 选择业务知识、项目运行模型、功能知识或数据知识子能力 |
| `3. 路由系统` | `router` | 固定门禁 | 从 `flows/` 选择一个完整执行流程 |
| `4. 执行系统` | `design` | 条件能力 | 为复杂变更形成可执行、可验证的稳定设计 |
|  | `dev` | 执行能力 | 完成预期明确的功能或行为变更 |
|  | `debug` | 条件能力 | 只读定位未知根因并形成反馈请求 |
|  | `fix` | 条件能力 | 对已证实缺陷实施最小修复和回归 |
|  | `it-test` | 条件能力 | 从真实 HTTP/API 入口完成完整链路验收 |
| `5. 审计系统` | `audit` | 固定门禁 | 独立、只读审计交付候选或知识候选 |
| `6. 交付系统` | `cr` | 固定门禁 | 组织人工 Review、记录决定与授权并完成受控交付 |
| `7. 演进系统` | `retro` | 条件能力 | 基于运行证据提出 Harness 改进候选 |
|  | `skill-creator` | 维护能力 | 创建获批的 Harness 新 Skill |
|  | `skill-neat` | 维护能力 | 迭代已进入维护状态的 Harness Skill |
| `8. 横向能力` | `subagent` | 横向能力 | 统一临时分支、上下文隔离、并行与结果回收 |
| `9. 额外能力` | `biz` | 条件能力 | 通过持续交互解决阻断性的业务认知缺口 |
|  | `mock` | 条件能力 | 显式管理 Mock 平台接口契约 |

一级目录使用上表中文编号，第二级目录使用 Skill ID。`subagent` 属于横向能力，可被多个系统加载，但不因其拥有 Skill 载体就成为独立流程节点。

业务项目初步固定投影 13 个 Skill；`cooper`、`biz`、`mock` 是按项目与任务条件接入的三个扩展能力。`skill-creator` 与 `skill-neat` 只服务 Harness 演进控制面，不安装到业务项目。“已实现”只表示源码和直接合同形成，不表示每次任务都要加载或已经通过真实主链验证。

## 三、核心能力合同

### 1. 意图与材料

- `intent` 区分用户意图与项目事实，只确认会改变结果的缺口；未确认不得下游。
- `cooper` 在本系统中只承担指定材料的最小只读访问。现有平台管理、发布和协作者操作不随
  意图接入自动获得授权。
- `biz` 即使由 `intent` 触发，也属于额外能力；完成后把已确认业务事实和未知项交还
  `intent`，不直接进入开发。

### 2. 知识

- `know` 在正常任务中从各类项目知识源检索、核验并整合信息元，形成下游可直接消费的任务
  信息集合；交付后只对最终稳定且有持续价值的变化进行日常沉淀。
- `know/SKILL.md` 只按当前运行阶段选择项目知识检索或项目知识沉淀子能力；两个子能力分别
  定义自己的输入、产物、执行和验收规则，不自动调用或加载对方。
- `know` 沿用现有知识结构，不建设或调整整体结构，也不调用或选择 `build`。
- `build` 只在项目接入流程明确要求或用户手动调用时运行；其 `SKILL.md` 只选择业务知识、
  项目运行模型、功能知识或数据知识子能力。
- 四个子能力彼此独立，各自定义事实来源、建设结构、执行方法和验收规则；没有共同建设流程、
  前后依赖或由 `build` 统一处理的知识内容。
- `build` 不进入业务任务路由；日常任务中的知识缺口由 `know` 如实暴露，不自动触发
  知识体系建设。

### 3. 路由与执行

- `router` 只选择完整流程，不执行能力、管理状态或决定产物失效。
- `design` 同时给出可判断的验收条件和关键测试范围，不再设置独立 `test-design` 节点。
- `dev`、`fix` 在自身范围内选择白盒测试、编译和静态检查；白盒测试不是独立 Skill。
- `it-test` 的显示名为 `IT-test`，保留真实 HTTP 验收内核；语言、框架、Fixture 和模板进入
  项目规则、Profile 或资产。
- 编码规范由用户与项目规则、语言或项目 Profile 以及确定性检查共同承载，不设置
  `coding-standards` Skill。

### 4. 审计、交付与演进

- `audit` 定义审计包、证据要求和报告合同；专用 Audit Agent 承载固定只读角色。发现问题或
  证据不足均不得通过，审计本身不修复对象。
- `cr` 组织最小人工 Review 包，处理基于现有事实的审查疑问，记录反馈、人工修改、决定与授权，
  并在授权范围内完成或核验外部交付；它只向 Harness 返回结果，不自行选择后续流程。
- `retro` 只解释可验证运行证据并提出改进候选；获批候选直接进入 Harness 演进控制面，不进入业务 `intent`。
- `skill-creator` 与 `skill-neat` 分别承担新 Skill 创建和已有 Skill 迭代；其他 Harness 产物由对应实现能力维护。
- Harness 改进实施后必须执行与影响匹配的审计和效果验证，经必要人工确认，并保留回退方式与演进记录。

## 四、项目知识建设

```text
项目接入要求或用户明确调用 build
→ build 识别目标知识类型
→ 加载对应的独立子能力
   ├── 业务知识
   ├── 项目运行模型
   ├── 功能知识
   └── 数据知识
→ 各子能力独立形成候选
→ 各候选分别经过知识审计与必要批准
→ 对应子能力分别应用并验证
→ 结束，不进入业务任务流程
```

四项能力作为 `build` 的独立子能力维护。`build/SKILL.md` 只负责选择和加载；首次接入分别执行
全部子能力，手动调用只执行命中的子能力。一个子能力的结构、过程和结论不约束其他子能力。

## 五、现有能力收敛

| 当前能力 | 目标处理 | 必要规则去向 |
|---|---|---|
| `project-runtime-model` | 迁入 `build` 子能力 | 由项目运行模型子能力独立建设与验证，`build` 只负责选择 |
| `test-design` | 不保留独立 Skill | 验收规格进入 `design`；测试实现和执行进入 `dev`、`fix`、`it-test` |
| `coding-standards` | 不保留独立 Skill | 通用规则进入 `AGENTS.md`；语言和项目差异进入 Profile；确定性规则进入工具 |
| `unit-test` | 不保留独立 Skill | 白盒测试选择与执行进入 `dev`、`fix` |
| `integration-test` | 改为 `it-test` | 保留真实 HTTP 内核，项目差异进入 Profile 或资产 |
| `subagent` | 复制到 `8. 横向能力` | 公共编排边界仍归 runtime 与项目规则；Skill 统一分支、隔离、独立验证和回收行为 |
| `use-power` | 继续移除 | 流程定义归 `flows/`，选择归 `router` |

## 六、运行关系

Skill 只负责自身能力，整体闭环由 `runtime/` 维护：

```text
业务交付面：intent → know → router → 执行流程 → audit → cr
交付后：know 沉淀与知识审计；运行证据 → retro
项目知识建设：接入要求或用户调用 → build → audit 与必要批准 → 应用并结束
Harness 控制面：改进候选 → 人工批准 → 维护实施 → 审计与验证 → 应用/回退
```

完整分支、回流、产物失效和恢复分别以
[`runtime/系统流程.md`](../../runtime/系统流程.md)、
[`runtime/整体编排/任务交付闭环.md`](../../runtime/整体编排/任务交付闭环.md)和
[`runtime/整体编排/系统演进闭环.md`](../../runtime/整体编排/系统演进闭环.md)为唯一事实来源。
