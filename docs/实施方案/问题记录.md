# Harness Engineering 问题记录

本文只记录会影响真实试运行、启用或稳定接入的未解决问题。目录、Skill 边界和“任务信息集合”
合同已经实现的事项不再作为开放问题保留。

## 一、知识与运行

1. 首个试点项目中，业务知识、项目运行模型、功能知识和数据知识各自以哪些现有文件作为权威
   来源，内部索引放在哪里，怎样验证时效与引用？
2. 任务信息集合中的信息元在真实复杂任务中需要多大粒度，才能既让执行直接消费，又不复制
   无关全文或隐藏原始冲突？
3. Audit Agent 的只读权限如何在当前运行环境中形成可验证的硬约束；哪些只能保留为行为规则？
4. 如何以足够低的成本记录耗时、Token、返工和人工介入，供 `retro` 使用？

## 二、接入与试运行

1. 哪个经授权的低风险业务项目适合作为正常链试点，哪个任务适合验证审计失败、人工反馈或
   意图变化？
2. 业务项目应如何引用 `.harness/runtime/HARNESS.md`，才能既自动生效又不覆盖其现有
   `AGENTS.md` 规则？
3. 实验接入工具在真实项目中的 Skill 发现、同名冲突、并发修改、真实升级和解除后重接入是否成立？
4. 以哪些正确性、人工打断、返工、耗时和维护成本证据决定某个能力可以从“初步实现”标记为
   “已启用”？

## 三、Harness 演进

1. 哪些运行证据足以提出 Harness 改进，哪些仍需补充验证？
2. 如何界定演进任务的范围、验收、授权和回退条件？
3. 如何隔离演进实现与业务项目交付，避免控制面变化污染正在执行的任务？
4. 如何验证一次 Harness 改进有效且没有引入新的路由、上下文或协作退化？
