# Harness Engineering 实施路线图

## 一、目的

本文定义 Harness Engineering 从架构到实践的建设顺序，维护阶段、任务、产出和推进门禁。

## 二、实施主线

```text
初步设计 → Skill 目录与能力实现 → 整体编排试运行 → 程序化接入 → 实践验证与演进
```

### 1. 子系统设计

定义七个主流程系统的职责与产出、最小 Skill 拓扑、横向能力边界和整体运行闭环。本阶段只
确定实施载体、能力合同和回流原则，不把 Skill 正文、Agent 配置、状态字段或程序实现写成
已经落地。

### 2. 子系统能力实现

按意图、知识、路由、执行、审计、交付、演进顺序逐个实现能力。每个子系统以完整主流程为参照，只修改本系统及直接交接方，并同步维护运行入口、流程、Skill 和项目规则。

### 3. 整体编排与试运行

- `runtime/系统流程.md` 维护跨系统主流程与状态；
- `runtime/整体编排/任务交付闭环.md` 维护单次开发任务的触发、交接、失效、回流和终止；
- `runtime/整体编排/系统演进闭环.md` 维护知识与 Harness 的跨任务演进。

整体编排是跨系统状态、反馈回流和任务生命周期的唯一权威载体，不重复子系统内部方案。

完成最小主链后接入一个真实低风险任务，分别验证正常交付和问题回流；未经过真实任务的能力不标记为已启用。

### 4. 程序化接入

项目初始化、检查、更新和解除接入可以先形成不编排 Prompt 的实验工具；只有真实流程稳定并
完成试点后，才能把接入合同和确定性门禁标为稳定。

### 5. 实践验证与演进

用真实开发任务观察交付正确性、遗漏与返工、执行效率和维护成本。只有验证有效的能力才进入稳定实践，并由此决定新系统与现有 SOP 是合并、并行还是替代。

## 三、后续任务

### 1. 子系统功能实现

每个子系统都以对应的 `docs/子系统设计/` 文档为实施输入，按同一小闭环完成：先确定本系统
稳定输入输出，再实现 Skill、规则或 Agent，检查直接上下游交接，最后完成静态校验和隔离
行为验收。实施中只同步状态与直接引用；发现设计缺陷时进入问题记录并与用户对齐，不在实现
任务中静默改架构。

| 任务 | 状态 | 实现内容 | 主要产出 | 完成门禁 |
|---|---|---|---|---|
| S0 Skill 目录迁移 | 已初步完成 | 按 `1. 意图接入系统` 至 `9. 额外能力` 的分类迁移保留能力，横向 `subagent` 和演进维护 Skills 保持 Harness 隔离副本 | `skills/<编号. 分类>/<skill>/` | 旧路径和失效引用清理；本机能力继续被忽略 |
| S1 意图接入 | 已完成首次创建 | 用 `intent` 收敛目标、范围、验收、约束和授权，支持待确认与阻断性修订 | 已确认任务意图、待确认意图 | 清晰任务、实质歧义、下游事实反馈三类隔离复演通过；真实主链前保持未启用 |
| S2 知识系统 | 已初步实现，待行为验收 | `know` 检索项目知识、整合任务信息元并受控沉淀持久变化；`build` 在接入要求或用户调用时选择四个独立知识建设子能力 | 任务信息集合、各子能力的知识建设结果、知识沉淀结果 | `build` 不进入日常流程且不统一子能力过程；信息元可直接消费并保留来源、状态和边界；知识写入经过门禁 |
| S3 路由系统 | 已初步实现，待行为验收 | 用任务信息集合补全初始与反馈路由合同；`router` 只从 `flows/` 选择一个完整流程 | 选定工作流程、Skill 名称与执行输入 | 正向、排他、输入不足和反馈回流用例通过；路由不执行功能 Skill 或管理状态 |
| S4 执行系统 | 已初步实现，待行为验收 | 适配 `design`、`dev`、`debug`、`fix`、`it-test`；把验收规格、白盒测试和编码安全规则迁入正确载体 | 技术设计、候选代码、执行证据、反馈请求 | 四条执行流程能停止、交互和交接；真实入口验收不被 Mock 或模型判断替代；不以自验代替独立审计 |
| S5 审计系统 | 已初步实现，待行为验收 | `audit` 定义交付与知识双门禁；正式运行使用干净只读上下文 | 审计包、审计报告、反馈事实 | 干净上下文只读运行；发现问题或证据不足均不通过；审计不直接修复对象 |
| S6 交付系统 | 已初步实现，待行为验收 | `cr` 组织最小人工 Review 包、反馈请求、人工修改影响和外部操作回执 | 交付审查包、反馈请求、交付结果、最终事实来源 | 审计通过不自动交付；`cr` 不直接选择执行能力；人工修改后旧审计失效 |
| S7 演进系统 | 已初步实现，待行为验收 | `retro` 复盘运行，`skill-creator` 和 `skill-neat` 受控实施 Skill 改进，其他维护由对应实现能力承担 | Harness 复盘报告、改进候选、维护产物、验证与演进记录 | 人工批准后才维护；不进入业务 `intent`；实施结果可审计、可验证、可回退 |

`test-design`、`coding-standards`、`unit-test` 不再作为目标独立 Skill；迁移时只把仍必要的规则
并入 `design`、`dev`、`fix`、项目规则或 Profile。`integration-test` 收敛为 `it-test`。

### 2. 整体运行实现

初步运行文档已经形成，但仍需在能力实现后接入真实状态和产物，不让单个 Skill 自行承担全局状态：

| 任务 | 实现内容 | 主要产出 | 完成门禁 |
|---|---|---|---|
| R1 状态与产物合同 | 初步实现系统流程与运行记录模板；待真实任务补运行证据 | `runtime/系统流程.md`、`runtime/运行记录模板.md` | 每个状态只有一个负责系统；状态与文档存在性分离；所有回流有恢复条件 |
| R2 单任务闭环 | 初步设计已完成；能力实现后跑通正常链和问题回流 | `runtime/整体编排/任务交付闭环.md` | 正常链和至少一条问题回流链可由同一入口完整执行，无跨系统自行跳转 |
| R3 跨任务演进闭环 | 初步设计已完成；能力实现后验证知识和 Harness 两类演进 | `runtime/整体编排/系统演进闭环.md` | 项目知识与 Harness 改进分流；高影响写入和改进均有人工门禁 |
| R4 运行入口收敛 | 已形成装载顺序、初步运行方式和公共门禁，引用上述权威编排文件 | 可执行的 Harness 运行入口 | 新会话能从入口找到当前阶段、应加载能力、停止条件和交接对象；真实项目仍需验证 |

### 3. 接入真实项目

先手工试运行，再固化自动化。当前 Codex 会从工作目录到仓库根扫描 `.agents/skills`，并支持
Skill 目录软链接；`AGENTS.md` 则按仓库根到当前目录逐层加载，同一目录只取一个指令文件。
因此 Harness 的分层源码不能直接当成项目发现目录，接入层需要生成扁平投影，而不能改变
Harness 源码结构。产品行为以 OpenAI 官方的 [Skills 文档](https://developers.openai.com/codex/skills/)
和 [AGENTS.md 文档](https://developers.openai.com/codex/guides/agents-md/) 为当前依据，实施时重新核验。

| 任务 | 实现内容 | 主要产出 | 完成门禁 |
|---|---|---|---|
| P1 手工接入规格 | 选择一个经用户授权的低风险业务项目；将所需 Harness Skill 逐个扁平映射为目标项目 `.agents/skills/<skill>`，每个链接解析到 Harness 根目录下真实的 `skills/<编号-职责>/<skill>`，不按业务项目目录解释；显式加载 Harness 运行入口，同时保留业务项目规则 | 试运行接入清单、Skill 投影、指令来源清单 | Codex 能发现预期 Skill 且没有同名重复；每个链接目标存在、位于预期 Harness 根且与清单一致；业务规则仍是项目事实来源；未覆盖或替换普通用户内容 |
| P2 正常链试运行 | 用一个真实低风险开发任务跑通意图、知识、路由、执行、审计和交付 | 完整稳定产物、运行证据和交付结果 | 真实任务完结；各阶段输入输出可追溯；未用模型自述代替测试、审计或人工确认 |
| P3 问题回流试运行 | 再选择一个会触发审计失败、人工反馈或意图变化的任务，验证失效、回流、重新审计和交付 | 问题回流证据、修订产物和第二次交付结果 | 没有静默扩大范围；旧审计在修改后失效；恢复节点正确且没有全链重做 |
| P4 启用判断 | 汇总两次真实运行中的正确性、人工打断、返工、耗时和维护成本，决定哪些能力可以标为启用 | 试运行结论、保留问题和下一轮改进任务 | 只启用已有真实证据的能力；未通过节点继续标记未启用 |

手工接入阶段不要求先修改目标项目永久规则。若必须让 Codex 自动加载 Harness 入口，先在试点
中比较“目标 `AGENTS.md` 的受管最小片段”和“受管片段只要求读取独立 `HARNESS.md`”两种方式；
以实际加载和冲突验证决定最终形式，不用文档推测固化接入协议。

### 4. 程序化接入

已先实现不编排 Prompt 的实验接入工具 `scripts/harness.py`；P1—P4 完成前不得把它标记为
稳定接入协议：

| 子任务 | 行为 | 验收重点 |
|---|---|---|
| `init` | 预检目标目录与同名冲突，建立受管清单、扁平 Skill 软链接和运行入口；不覆盖普通文件或差异副本 | 临时目录已验证首次与重复接入；真实项目加载仍待验证 |
| `doctor` | 只读检查受管清单、源码变化、Skill 链接目标、运行入口和项目 Git 边界 | 已区分物理接入完整性与真实流程尚未验收；真实项目同名组合待验证 |
| `update` | 根据受管清单更新入口和投影，只处理工具拥有的内容，发现用户修改时阻断 | 用户改动阻断、受管集合变化和模拟失败回滚已验证；真实升级待验证 |
| `remove` | 只移除受管链接、入口和清单，保留业务规则、项目知识与普通 Skill | 临时目录完整解除已验证；真实项目重接入待验证 |

工具实现后在临时 Git 仓库验证首次接入、重复接入、部分失败恢复、升级冲突和解除接入，再对
真实试点项目执行；脚本只固化已经验证的接入不变量，不负责 Prompt 流程编排或业务交付。

### 5. 实际推进顺序

```text
初步实现整体验证
→ P1 低风险项目接入 → P2 正常链 → P3 问题回流 → P4 启用判断
→ 收敛 init/doctor/update/remove → 持续实践与演进
```

当前初步实现按用户要求一次形成完整候选，但验收仍按子系统和主链分层进行。下一项是清理
旧引用、完成静态与隔离行为验收，然后进入真实低风险项目试点。
