# Harness Engineering 系统设计

> 当前版本：整体结构重构中的初步系统设计。Harness 尚未启用，以下内容仍需经过隔离验证和真实任务试运行。

## 一、框架与领域实例

Harness 本质上是围绕 Agent 和 LLM 的运行与编排框架，不由某一领域的流程、子系统数量或 Skills
清单定义。框架负责跨领域稳定的全局编排职责、信息所有权、扩展边界、治理和演进规则。

当前项目实现的是软件工程领域实例。它在框架边界内定义软件任务需要的子系统、整体开发编排、
过程产物、结果产物和具体能力。未来可以接入运营社交平台、AI 视频生产等其他领域实例；不同领域
可以采用不同子系统与流程，不要求复用软件工程五个业务任务职责域。

系统按三层区分：

| 层次 | 负责什么 |
|---|---|
| Harness 框架 | 全局运行与编排、信息和产物所有权、领域扩展接口、确定性治理边界及框架演进 |
| 领域实例 | 特定领域的子系统、职责、整体编排、过程产物、结果产物和领域门禁 |
| 具体实现 | Skills、脚本、模板、连接器、Agent 配置和宿主适配 |

规则、问题和修改必须先判断属于框架、领域实例还是具体实现。领域实例中的一次问题不自动成为框架
规则；框架变化必须检查对现有领域实例的影响；具体实现不得反向覆盖未确认的上层设计。

框架层确认以下信息所有权：

- Harness 管理子系统的进入与跳过、输入交接、产物引用与有效性、反馈回流、验证与审计门禁，以及
  最终结果汇总；
- 子系统和功能型 Skill 管理自身产出的内容结构、生成方法和质量规则；
- 业务项目保存代码、设计、测试、项目知识等正式资产，Harness 只管理其引用和任务中的使用状态；
- 运行记录和框架改进证据由 Harness 最小化管理，演进能力按受控流程消费，不由单个子系统私有维护。

## 二、当前软件工程领域实例

当前软件工程 Harness 是在人工治理下、由用户意图驱动的 AI Coding 工程系统。它不把模型、单一
文档、代码、测试或最终回答视为绝对真相，而是用可组合能力、运行时约束和真实证据支持软件任务。

当前领域任务运行和 Harness 框架演进分属两个控制面：

- **业务任务运行面**：服务具体代码仓库中的任务，处理意图、事实、能力执行、验证、审计和知识
  沉淀，向用户呈现计算机侧结果，并只在获得明确授权后执行相应外部操作。
- **Harness 演进控制面**：属于框架层，只维护 Harness 自身，根据运行证据和反馈提出、验证、采纳
  或回退系统改进。

人负责目标、范围、例外裁决、风险接受、外部授权以及是否启动 Harness 改进。业务项目的需求事实、
代码、项目知识和项目规则仍由业务项目维护，不写入本仓库。

宿主主会话是默认执行主体。Skill 是主会话按需加载的能力与规则单元，不代表独立角色；代码阅读、
修改和常规工具使用属于 Agent 自身能力。只有上下文隔离、并行或独立判断确有价值时，主会话才创建
Subagent；Subagent 的结果仍由主会话回收并继续执行。

Harness 只管理 Agent 能够观察和执行的计算机侧工作，不建模、约束或替用户完成现实中的人工验收、
风险接受、发布与回退。它只接收用户实际给出的决定和反馈。Agent 发起 Commit、Push、PR、部署、发布
或其他外部写入时必须获得明确授权，并优先由 Hook、命令前检查或宿主审批等确定性机制保护。

## 三、总体架构原则

1. **职责域不是固定流水线**：当前软件工程实例的五个任务系统定义判断和产物归属，能力根据当前需求、事实和风险按需组合；Harness 演进使用独立控制面。
2. **HARNESS 全局调度**：HARNESS 决定是否进入意图、知识或路线规划，让主会话按路线加载能力，处理反馈与重新规划，并汇总当前请求的计算机侧结果。
3. **Router 规划开发路线**：Router 优先复用代表性任务场景选择当前需求所需的具体能力、执行顺序、稳定产物、测试策略和审计门禁；没有适用场景时再根据实际复杂度与影响补充判断，但不直接执行能力。
4. **主会话执行、Skill 提供能力**：主会话是默认执行者；Skill 负责被加载后约束或增强当前工作，不自行决定是否运行、下一个能力或跨系统回流。
5. **意图与事实分离**：用户决定想要什么，项目来源和运行证据说明当前是什么；`intent` 和 `know` 均按需进入，不是固定前置阶段。
6. **场景复用与最小路线**：常见任务优先复用已经定义的路线场景，简单任务保持最短有效路径；只有场景不适用或实际影响扩大时才重新判断，不让 Router 每次从零推演全部可能性。
7. **确定性规则优先**：能由权限、工具限制、分支检查、路径检查或脚本判断的约束，不只依赖 Prompt 自述。
8. **真实证据优先**：模型判断、静态检查、Mock 和编译结果不能代替真实入口、外部回执或人工决定。
9. **需求相关与最小修改**：实现和审计都围绕当前需求，保护未要求改变的存量行为，不以理论风险或顺手治理扩大范围。
10. **必要可回查**：稳定产物、验证结论和 Agent 实际执行的外部操作能够回到当前来源、差异与真实结果；不为此预设通用版本对象、任务状态机或知识版本模型。
11. **人机边界**：Harness 完成当前计算机工作并返回结果后停止；用户是否接受、是否继续以及如何发布属于用户决定，不建立持久化“任务结束”仪式。
12. **输入边界**：当前范围假设交给 Agent 的项目和材料已经完成必要处理并允许使用，不另建敏感信息识别与脱敏子系统；业务项目和宿主平台现有安全规则仍然适用。

## 四、软件工程实例的五个任务职责域与框架演进控制面

| 层面 | 职责 | 负责什么 | 当前公开能力 |
|---|---|---|---|
| 软件工程实例 | 意图接入 | 对齐目标、范围、验收、约束和授权缺口 | `intent` |
| 软件工程实例 | 知识 | 定位、核验、整合任务事实，受控沉淀长期知识 | `know`、`build` |
| 软件工程实例 | 路由 | 规划需求的具体执行能力、顺序、稳定产物、测试策略和审计门禁 | `router` |
| 软件工程实例 | 执行 | 主会话加载设计、测试设计、诊断、编码约束和测试能力完成工作 | `tec-design`、`test-design`、`coding`、`debug`、`unit-test`、`it-test` |
| 软件工程实例 | 审计 | 独立核验需求覆盖、改动边界、存量影响、实现质量和验证证据 | `audit` |
| Harness 框架控制面 | 演进 | 复盘运行证据，受控维护 Harness 自身 | `retro`、`skill-creator`、`skill-neat` |

`subagent` 是横向的上下文隔离、并行、独立验证和结果回收能力，不是独立时序节点。`cooper` 与
`mock` 是仅限本机的能力目录，永久不进入公开仓库；是否在本机业务项目中投影，另按接入条件和授权决定。

五个业务任务职责域、框架演进控制面、横向能力和现有编号目录组成当前能力拓扑。后续仍可基于职责
与真实任务证据调整；不能把演进控制面并入软件工程业务任务链，也不能把数量、编号或当前目录名称
提升为框架约束。

## 五、软件工程实例的运行编排

`runtime/HARNESS.md` 是业务项目唯一需要加载的运行合同。本仓库的 README、AGENTS、TODO、Skill
正文和脚本实现不属于业务项目运行时合同。

HARNESS 由宿主主会话解释执行，当前不预设独立状态机。它按以下循环工作：

1. 读取当前用户输入和业务项目规则；只有实质歧义会改变后续行动时才进入 `intent`。
2. 使用已有需求和事实请求 `router` 形成开发路线。项目存在知识入口且缺少的共享事实会改变路线时，
   HARNESS 才调用 `know` 后重新规划；没有知识库时直接跳过任务前知识检索，主会话和执行 Skill 按需
   读取当前代码、项目规则与用户材料。
3. Router 优先匹配已定义的代表性任务场景，选择具体能力及顺序，并决定是否需要技术设计、独立设计
   或测试文档、测试设计、TDD、`unit-test`、`it-test` 及独立审计；场景不适用时再根据实际复杂度与
   影响补充路线。
4. 主会话按路线逐项加载并执行能力。需要修改生产代码时，代码实现由主会话完成，同时加载 `coding`
   的个性化编码习惯和本机环境约束；是否将该过程进一步收敛为 `dev` 由后续设计决定。
5. HARNESS 接收节点结果并继续路线。用户目标或验收变化、项目事实推翻路线依据、节点无法按路线
   执行、实际影响面明显扩大，或测试、审计与人工反馈要求改变环节时，才重新调用 Router。
6. 路线中的执行与验证形成稳定结果后，HARNESS 判断是否产生需要长期维护的项目知识变化；需要时
   调用 `know`，由它从过程产物、稳定结果和可回查事实中提取知识。项目没有现成知识库时，也允许为
   本次确有持续价值的结果建立最小知识入口，不以未执行完整 `build` 为阻断条件。
7. 知识候选未被当前审计对象覆盖时，HARNESS 重新调用 Router 补充知识审计门禁；候选通过审计、
   必要确认后，再由 `know` 写入并回读验证。HARNESS 最终向用户汇总当前计算机侧结果、知识沉淀结果、
   验证边界、审计结论和剩余问题；用户是否验收和是否继续由后续输入自然表达。

Router 只决定是否需要稳定产物及其用途，不决定产物的内容、结构、模板和保存位置；对应 Skill 负责
专业内容，正式代码、设计、测试和项目知识由业务项目在原位置维护。简单任务可以全部留在会话中，
不要求建立任务文件或状态对象；确需跨能力、跨会话或审计时，HARNESS 只维护必要的全局进展和引用。

审计以本次需求和实际差异为锚点，检查需求覆盖、所有修改的相关性、存量代码或行为变更的必要性、
是否存在更小影响方案、实现是否简洁，以及是否遵守项目架构并具备匹配风险的验证证据。审计只扩大到
本次改动引入、扩大或直接触达的现实风险；无关存量问题和没有实际触发路径的理论风险不得自动扩大
任务或阻断交付。

需要独立审计时，主会话根据 `audit` 的规则创建干净上下文的 Audit Subagent。Audit Subagent 只返回
问题、证据和建议，主会话负责判断和修改，再交回复审；`audit` 需要限制协商轮次并给出分歧停止条件，
避免审计阶段演变成无限 Agent 对话。具体 Prompt、计数和复审协议归 `audit` Skill。

项目知识是由知识系统单独维护的正式资产。设计、测试、代码、运行结果和其他过程产物可以作为知识
提取来源，但不会因自身存在自动成为项目知识，也不替代业务知识、项目核心运行模型、功能知识和
数据知识等既定知识内容。

`build` 是用户按需启动的首次或结构性知识建设能力，不是 Harness 启用门禁。新项目主要通过用户
信息源和连续问答建设，存量项目结合代码事实、已有材料和用户信息建设；具体问答协议、总目录和四类
知识结构继续在知识系统设计中收敛。

人工 Review、风险接受、发布和回退是用户行为，不由 Harness 建模或控制。`cr` 是用户审阅候选后主动
触发的个人反馈对齐能力，不进入 HARNESS 的路线、调度或默认项目投影。Agent 需要执行外部写入时，
只处理用户明确授权的具体计算机动作，并如实返回工具结果。

业务任务运行面和 Harness 演进控制面不能共享隐式状态。`retro` 从可获得的任务证据提出 Harness
改进候选；用户决定是否另行启动维护任务。维护任务负责修改与验证，Release、发布和回退仍属于用户
授权的仓库维护操作，不由 Retro 自动执行。

## 六、项目接入与领域扩展

项目接入采用“确定性 CLI 核心 + AI 辅助交互”。AI 可以判断目标项目是否适用、解释选择并组织参数，
但绑定结果统一由 `scripts/harness.py` 产生。当前不建设 TUI，也不让 Prompt 直接执行一套无法重复的
文件操作。

本仓库的 AI 接入对话由 `AGENTS.md` 按操作意图加载 `command/<命令>.md`，一条命令一个文件。
提示词只负责必要交互、脚本调用和结果解释；确定性检查、文件操作及恢复由 Python 负责，不在提示词
中重复维护。命令指引不进入业务 Runtime，也不作为业务 Skill 投影；对话入口尚待真实会话验证。

领域实例通过 `systems/<system-id>.json` 注册。Manifest 声明系统 id、显示名称、Runtime，以及默认、
条件、本机、横向、个人和 Harness 演进能力；它是接入工具的能力注册表，不是 HARNESS 运行时的任务
路线。当前只有 `software-engineering`，因此可以自动选择；未来增加领域实例不需要修改既有实例或把
软件工程职责域提升为框架固定结构。

第一版使用规则文件加载器：

1. `init` 选择领域系统和目标项目，在已有 `AGENTS.md`、`CLAUDE.md` 中写入最小受管入口；两者都
   不存在时，由交互或显式参数决定创建哪个文件。
2. 目标项目 `.harness/runtime/HARNESS.md` 软链接到本仓库唯一 Runtime；默认与横向 Skills 自动
   平铺软链接到 `.agents/skills/<skill>`，条件与本机 Skills 只在显式选择时投影，不复制或重新分组源码。
3. 目标项目 `.harness/manifest.json` 是绑定事实，记录原项目、领域系统、规则入口和可选能力；本仓库
   `data/projects.json` 只用于列出和定位已绑定项目，不覆盖目标项目清单。索引缺失或损坏不得
   阻断项目级检查、修复或解绑；`relink` 可隔离内容损坏的普通索引并重建当前项目记录，非普通文件
   占用索引路径时只报告精确冲突，由用户移走后再重建。
4. `relink` 复用目标项目清单重新建立 Runtime、Skills、规则入口和本机索引，用于链接损坏、Harness
   源目录移动和能力清单同步；它不重新选择项目或领域系统。
5. `doctor` 只检查并给出修复提示，`remove` 只解除受管内容，`list` 只读取本机索引。实时软链接不再
   需要独立 `update` 命令。

本地辅助数据统一放在 Harness 源目录下的 `data/`，不受命令执行目录影响，也不写入用户主目录。
`projects.json` 保存该仓库记录的项目索引，`locks/` 保存文件锁，`backups/` 按需保存损坏索引备份；
整个目录由 Git 忽略，不随源码共享。目标项目清单不依赖该索引，索引丢失时可逐项目运行 `relink` 重建。

Hook 是未来可增加的宿主加载适配器，不是第一版启用条件。只有真实使用证明规则入口不足、且具体
宿主具备稳定 Hook 能力时，才根据上下文、Token、时延、可观察性和失败降级设计；无论增加哪种
适配器，`runtime/HARNESS.md` 仍是唯一运行合同。

## 七、能力载体边界

- `AGENTS.md`：本仓库的维护规则、公开边界和长期协作约束。
- `README.md`：项目定位、当前状态、目录入口和使用说明。
- `command/`：本仓库接入助手的分命令轻量提示词。
- `TODO.md`：变化中的实施计划、依赖、门禁和未决问题。
- `docs/系统设计.md`：稳定的整体架构、职责和设计原则。
- `docs/外部实践与设计候选.md`：外部资料提炼和待讨论候选，不属于稳定设计或实施计划。
- `runtime/HARNESS.md`：业务项目运行时的公共合同。
- `systems/`：领域实例的接入 Manifest 和能力投影边界。
- `skills/`：单项能力的触发边界、输入、输出、执行规则和停止条件。
- `scripts/`：仓库维护、能力投影和业务项目接入工具，不编排 Prompt 流程。
- `subagent`：临时上下文分叉或独立验证机制，不改变公共事实和验收预期。

同一事实只在一个载体中完整维护。跨系统合同归 runtime，Skill 内部方法归 Skill，仓库维护规则
归 AGENTS，变化中的推进事项归 TODO。
