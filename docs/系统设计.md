# Harness Engineering 系统设计

> 当前版本：整体结构重构中的初步系统设计。Harness 尚未启用，以下内容仍需经过隔离验证和真实任务试运行。

## 一、框架与领域实例

Harness 本质上是围绕 Agent 和 LLM 的运行与编排框架，不由某一领域的流程、子系统数量或 Skills
清单定义。框架负责跨领域稳定的全局编排职责、信息所有权、扩展边界、治理和演进规则。

当前项目实现的是软件工程领域实例。它在框架边界内定义软件任务需要的子系统、整体开发编排、
过程产物、结果产物和具体能力。未来可以接入运营社交平台、AI 视频生产等其他领域实例；不同领域
可以采用不同子系统与流程，不要求复用软件工程七个职责域。

系统按三层区分：

| 层次 | 负责什么 |
|---|---|
| Harness 框架 | 全局运行与编排、信息和产物所有权、领域扩展接口、确定性治理边界及框架演进 |
| 领域实例 | 特定领域的子系统、职责、整体编排、过程产物、结果产物和领域门禁 |
| 具体实现 | Skills、脚本、模板、连接器、Agent 配置和宿主适配 |

规则、问题和修改必须先判断属于框架、领域实例还是具体实现。领域实例中的一次问题不自动成为框架
规则；框架变化必须检查对现有领域实例的影响；具体实现不得反向覆盖未确认的上层设计。

框架层确认以下信息所有权：

- Harness 管理子系统的进入与跳过、输入交接、产物引用与有效性、反馈回流、验证与审计门禁，以及
  最终结果汇总；
- 子系统和功能型 Skill 管理自身产出的内容结构、生成方法和质量规则；
- 业务项目保存代码、设计、测试、项目知识等正式资产，Harness 只管理其引用和任务中的使用状态；
- 运行记录和框架改进证据由 Harness 最小化管理，演进能力按受控流程消费，不由单个子系统私有维护。

## 二、当前软件工程领域实例

当前软件工程 Harness 是在人工治理下、由用户意图驱动的 AI Coding 工程系统。它不把模型、单一
文档、代码、测试或最终回答视为绝对真相，而是用可组合能力、运行时约束和真实证据支持软件任务。

当前领域任务运行和 Harness 框架演进分属两个控制面：

- **业务交付面**：服务具体代码仓库中的任务，处理意图、事实、能力执行、验证、审计和交付。
- **Harness 演进控制面**：属于框架层，只维护 Harness 自身，根据运行证据和反馈提出、验证、采纳
  或回退系统改进。

人负责目标、范围、例外裁决、风险接受、外部授权、高影响知识变化和 Harness 改进批准。业务项目的
需求事实、代码、项目知识和项目规则仍由业务项目维护，不写入本仓库。

## 三、总体架构原则

1. **职责域不是固定流水线**：当前软件工程实例的七个系统定义判断和产物归属，能力根据当前意图、上下文和风险按需组合。
2. **Runtime 统一编排**：进入、跳过、交接、失效、反馈、阻塞、恢复、终止和重新审计只由运行时解释。
3. **Skill 只负责自身能力**：Skill 不自行选择下一个 Skill，不管理跨系统状态，也不把缺口伪装成结论。
4. **意图与事实分离**：用户决定想要什么，项目来源和运行证据说明当前是什么。
5. **风险分级**：简单、低风险任务保持最短有效路径；复杂、高影响或有外部副作用的任务提升设计、验证、审计和人工门禁强度。
6. **确定性规则优先**：能由权限、工具限制、版本检查或脚本确定的约束，不只依赖 Prompt 自述。
7. **真实证据优先**：模型判断、静态检查、Mock 和编译结果不能代替真实入口、外部回执或人工决定。
8. **可追溯与可回退**：稳定产物、授权、验证和长期规则变化必须能定位来源、版本、依赖和撤销边界。

## 四、软件工程实例的七个职责域

| 职责域 | 负责什么 | 当前公开能力 |
|---|---|---|
| 意图接入 | 对齐目标、范围、验收、约束和授权缺口 | `intent` |
| 知识 | 定位、核验、整合任务事实，受控沉淀长期知识 | `know`、`build` |
| 路由 | 根据风险判断是否需要设计、稳定文档、测试设计和 TDD | `router` |
| 执行 | 执行已确认的设计、编码、诊断、测试和修复能力 | `tec-design`、`test-design`、`coding`、`debug`、`unit-test`、`it-test` |
| 审计 | 在需要时独立、只读、基于证据核验交付或知识候选 | `audit` |
| 交付 | 组织人工 Review、风险接受、授权和外部回执 | `cr` |
| 演进 | 复盘运行证据，受控维护 Harness 自身 | `retro`、`skill-creator`、`skill-neat` |

`subagent` 是横向的上下文隔离、并行、独立验证和结果回收能力，不是第八个时序节点。`cooper` 与
`mock` 是仅限本机的能力目录，永久不进入公开仓库；是否在本机业务项目中投影，另按接入条件和授权决定。

七个职责域、横向能力和现有编号目录是当前软件工程实例重构的输入，不是 Harness 框架要求，也不在
设计确认前把系统数量、编号或当前目录名称当作不可改变的实例架构。

## 五、运行时核心

`runtime/HARNESS.md` 是业务项目唯一需要加载的运行合同。本仓库的 README、AGENTS、TODO、Skill
正文和脚本实现不属于业务项目运行时合同。

运行时在任务执行中需要能够回答以下编排问题，但不要求每个任务建立独立状态对象或落盘。简单任务
可以直接使用当前对话和业务项目正式资产；只有跨子系统、跨会话继续或需要追溯时，才记录必要的
全局进展与产物引用：

- 当前意图和版本是什么，目标与范围是否仍有效；
- 当前启用或跳过了哪些能力，原因和负责方是什么；
- 交接了哪些输入、约束、未知项、证据和授权；
- 产生了哪些对象或产物，它们的版本、来源、依赖和有效性是什么；
- 哪些事件导致阻塞、恢复、失效、反馈、重新审计或终止；
- 最终验证、人工决定和外部操作的实际结果是什么。

运行时根据当前任务信息和风险组合能力。`router` 只输出风险路线判断，不选择或调用具体执行 Skill；
具体能力映射、上下文形态、权限边界和回收由运行时与能力清单共同决定。

运行时只统一管理产物的引用、流转、当前有效性和最终使用，不定义每个子系统产出的内部内容。子系统
返回自身结果和产物引用，正式代码、设计、测试和项目知识仍由业务项目在原位置维护。

业务交付面和 Harness 演进控制面不能共享隐式状态。演进改进必须经过证据、人工批准、实施、独立
验证、应用或回退，并记录演进结果。

## 六、能力载体边界

- `AGENTS.md`：本仓库的维护规则、公开边界和长期协作约束。
- `README.md`：项目定位、当前状态、目录入口和使用说明。
- `TODO.md`：变化中的实施计划、依赖、门禁和未决问题。
- `docs/系统设计.md`：稳定的整体架构、职责和设计原则。
- `docs/外部实践与设计候选.md`：外部资料提炼和待讨论候选，不属于稳定设计或实施计划。
- `runtime/HARNESS.md`：业务项目运行时的公共合同。
- `skills/`：单项能力的触发边界、输入、输出、执行规则和停止条件。
- `scripts/`：仓库维护、能力投影和业务项目接入工具，不编排 Prompt 流程。
- `subagent`：临时上下文分叉或独立验证机制，不改变公共事实和验收预期。

同一事实只在一个载体中完整维护。跨系统合同归 runtime，Skill 内部方法归 Skill，仓库维护规则
归 AGENTS，变化中的推进事项归 TODO。
