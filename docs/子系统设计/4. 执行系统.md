# 4. 执行系统

## 一、职责与产出

基于已确认任务意图、任务信息集合和选定工作流程执行对应 Skill，完成功能设计、实现和开发内
验证。执行系统可以核对关键原始证据，但不再按知识索引自行检索和拼装任务上下文。

具体步骤和产物由工作流程中的 Skill 决定；本系统只统一人机协作边界，并交出流程要求的稳定产物、候选代码和执行证据。

## 二、核心问题

1. 哪些不确定性必须由人决定，哪些应由 AI 自主处理。
2. 如何在需要人参与时最小化打断，又不让 AI 擅自改变结果。

## 三、解决方案

### 3.1 实施载体

由选定工作流程中的 Skill、工具和必要执行角色完成任务；产物类型、验证方式和节点顺序均服从该流程。

初步设计只保留五个执行 Skill：

- `design`：复杂变更的稳定设计、可判断验收条件和测试范围；
- `dev`：预期明确的新功能或行为变更；
- `debug`：未知根因的只读诊断；
- `fix`：已证实缺陷的最小修复和回归；
- `it-test`：真实 HTTP/API 完整链路验收，显示名为 `IT-test`。

不创建统一 `execution` Skill。需求级测试规格并入 `design`，白盒测试选择并入 `dev`、`fix`，
编码规范归用户或项目规则与 Profile；它们不是独立流程节点。

### 3.2 人机协作规则

出现以下情况必须请求人决定：

- 目标、范围、验收或既有意图需要改变；
- 权威信息源相互冲突，且无法用现有证据裁决；
- 存在多个会实质改变结果的设计选择；
- 缺少业务语义、外部授权或风险接受；
- 操作不可逆或会扩大已确认范围。

出现以下情况应由 AI 自主推进：

- 代码、文档、规则或运行证据能够回答；
- 选择可逆且不改变对外行为；
- 项目规范或工作流程已经给出默认规则；
- 常规编译、测试、工具失败和局部实现问题可在当前边界内处理。

问题属于需求变化、信息源缺失或流程不适用时，分别回到意图、知识或路由系统；其余必要交互在当前执行节点集中完成。

任何执行 Skill 都只返回问题、仍有效事实和恢复条件，不自行调用另一个系统完成跨系统跳转。

## 四、协作关系

```text
已确认任务意图 + 任务信息集合 + 选定工作流程及 Skill 索引
→ 执行与必要事实核对 → 必要人机交互
→ 流程规定的稳定产物 + 候选代码 + 执行证据 → 审计系统
```
