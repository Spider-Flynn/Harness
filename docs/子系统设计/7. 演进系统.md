# 7. 演进系统

## 一、职责与产出

演进系统维护 Harness 自身：从运行证据、用户反馈、审计问题和环境变化中识别改进，经人工批准后实施、验证、记录或回退。

产出包括 Harness 复盘报告、改进候选、维护产物、验证结果、演进记录和回退方式。本系统不处理业务项目需求或项目知识沉淀。

## 二、核心问题

1. 如何从运行证据和直接反馈中识别真实系统问题。
2. 如何把获批改进转化为边界清楚的 Harness 维护任务。
3. 如何选择正确维护能力，并保证改进可审计、可验证和可回退。

## 三、解决方案

### 3.1 输入

- 业务任务产生的会话记录、稳定产物和运行证据。
- 用户直接提出的 Harness 改进要求或失败案例。
- 审计发现的系统性问题。
- 模型、工具、运行环境或平台契约变化。

### 3.2 实施载体

- `retro` 在证据足够时复盘 Harness 运行，产出问题与改进候选，不自动修改系统。
- `skill-creator` 创建获批的新 Skill；`skill-neat` 迭代已进入维护状态的 Skill。
- 规则、流程、Agent、脚本、测试或门禁变更由对应实现能力承担，不强行归入 Skill 维护。
- 需要隔离分析、并行工作包或独立验收时加载横向 `subagent`。

### 3.3 演进门禁

- 复盘结论必须区分已证实问题、观察项与未覆盖范围。
- 人工决定是否实施、范围、验收、授权与风险接受；未批准候选不改变 Harness 当前事实。
- 维护任务直接在 Harness 控制面内执行，不进入业务 `intent`、`know` 或 `router`。
- 实施后根据影响执行静态检查、隔离行为验收或轻量真实任务验证；高影响变更使用独立审计。
- 只有验证通过且经必要人工确认后才应用改进；失败时按预先说明的回退方式恢复。

## 四、协作关系

```text
运行证据 / 用户反馈 / 审计问题 / 环境变化
→ retro 或直接形成改进候选
→ 人工批准
→ Harness 维护任务
→ skill-creator / skill-neat / 其他实现能力
→ 独立审计与效果验证
→ 应用或回退
→ 演进记录
```
