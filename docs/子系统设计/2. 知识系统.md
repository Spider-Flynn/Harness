# 2. 知识系统

## 一、职责与产出

维护项目长期信息源及其索引，在任务开始时产出由可追溯信息元组成、可直接消费的“任务信息
集合”，在交付确认后产出“知识沉淀结果”。

本系统决定信息源记录什么、如何组织、如何定位、如何整合和如何沉淀；下游不再根据索引自行
拼装任务事实，审计系统只提供沉淀门禁。

## 二、核心问题

1. 如何定义信息源类型、内容和边界，避免遗漏、重复与越权记录。
2. 如何定位、核验、去重并整合当前任务需要的事实，同时保留来源和不确定性。
3. 如何从最终稳定产物中识别持久变化，合并为当前有效知识。
4. 如何受控写入并验证知识、索引与项目事实一致。

## 三、解决方案

### 3.1 信息源体系

| 信息源 | 记录内容 |
|---|---|
| 业务知识 | 角色、业务对象、流程、规则、边界与例外 |
| 项目运行模型 | 核心对象、状态机、工作流、能力关系与关键数据流 |
| 功能知识 | 当前能力、设计原因、限制与验证边界 |
| 数据知识 | 数据库、DDL、数据语义、变更规则与测试数据元信息 |

四类是 `build` 建设的基线知识来源，不是 `know` 的检索白名单。任务需要时，`know` 也可以
读取项目规则和其他已确认信息，但不改变这些来源的权威归属。同一事实只归属一个权威信息源；
历史需求和失效方案不进入默认任务导航。

### 3.2 实施载体

- 用文档、结构化元数据和索引承载信息源；索引是知识系统内部定位机制，不是下游产物。
- `know/SKILL.md` 只按运行阶段选择项目知识检索或项目知识沉淀子能力；两个子能力分别维护
  自己的输入、产物、执行和验收规则，互不作为调用前提，也不自动触发对方。
- 用 `build` 独立建设项目知识体系：首次接入时作为启用前步骤明确触发，后续只由用户手动
  触发；它不进入正常任务流程，也不由 `know` 或 `router` 自动选择。
- 适合固定角色独立处理的检索或维护节点，可由预配置“知识 Agent”执行；是否形成临时 Subagent 由会话与 Agent 编排决定。
- 可确定的索引、引用、结构和一致性检查逐步程序化。

### 3.3 核心规则

- 先用索引定位候选来源，再读取当前任务所需的最小正文并独立核验；不能从索引标题直接推断事实。
- 任务信息集合由独立信息元组成；每项都保留内容、类别与对象、来源证据、适用范围、状态和
  验证边界。它不是来源目录、全文副本或未经判断的检索结果。
- 同一事实去重后只表达一次；来源结论不一致时保留冲突，不强行拼成单一事实。
- 信息源缺失、过期或冲突必须显式暴露，不以猜测补齐。
- 只有最终稳定产物形成持久变化时才进入沉淀，不要求每个任务更新知识。
- 待写入知识必须经过审计门禁；高影响变化和语义冲突由人裁决。
- 写入同时维护索引，并验证内容、引用和项目事实一致。

### 3.4 正常任务知识能力

任务前由项目知识检索子能力定位、核验和整合事实，产出由信息元组成的任务信息集合。交付后由
项目知识沉淀子能力判断持久变化、组织候选，并在门禁完成后写入和回读验证。`know/SKILL.md`
只选择当前阶段对应的子能力，不承载两项职责的具体流程。

### 3.5 知识体系建设

`build/SKILL.md` 只识别建设目标并加载业务知识、项目运行模型、功能知识或数据知识子能力。
四个子能力分别维护自己的事实来源、建设方法、结构和验收规则，没有共同建设流程或前后依赖；
`build` 不统一决定其内容结构，也不把一种知识的规则用于另一种知识。

首次接入分别执行四个子能力；用户再次调用时只选择其指定范围。正常任务发现知识不足时只暴露
缺口和影响，不自动进入 `build`。

## 四、协作关系

```text
任务前：已确认任务意图 → 信息定位、读取、核验与整合 → 任务信息集合 → 路由系统
独立建设：项目接入要求或用户明确调用 → build 候选 → 审计与必要批准 → 应用并验证
交付后：最终稳定产物 + 交付结果 + 事实来源
       → 知识组织 → 审计门禁 → 受控写入 → 写后验证
```
