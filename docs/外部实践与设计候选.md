# 外部实践与设计候选

> 状态：讨论输入，不是已确认系统设计，不代表实现计划或启用能力。
>
> 用途：保存最初提供的 18 份资料中值得继续讨论的原则、实现候选和适用边界。候选只有经过讨论
> 确认后才能进入《系统设计》；只有确定实施顺序后才进入 TODO。

## 一、当前已经确认的讨论边界

Harness 本质上是围绕 Agent 和 LLM 的运行系统，不等同于软件工程流程、当前五个业务任务职责域或一组 Skills。

当前仓库实现的是软件工程领域实例，包含该领域的子系统设计、能力实现和整体开发编排。未来可以
接入运营社交平台、AI 视频生产等领域实例。不同领域可以拥有不同的子系统和运行路线，也可能共享
演进、运行时、信息所有权、治理和评测等框架级能力。

这个扩展口当前只需在设计上保留，不建设通用多领域平台，也不因此推迟软件工程实例的整体设计。

以下三层边界已经确认；各层的具体合同仍需逐步讨论：

| 层次 | 讨论对象 |
|---|---|
| Harness 框架 | 跨领域的全局编排、信息和产物所有权、扩展边界、确定性治理及演进规则 |
| 领域实例 | 某领域需要哪些子系统、职责、依赖、进入条件、过程与结果产物及领域规则 |
| 具体实现 | Skills、脚本、模板、连接器、Agent 配置、宿主适配和确定性检查 |

规则、问题和修改应先按这三层判断归属。单个领域案例不能直接升级为框架规则，具体实现也不能反向
定义上层合同；暂时无法判断时只作为设计候选保留，等待讨论。

## 二、资料使用规则

这些资料是本地保存的文章文本或整理稿，本轮没有逐篇回到原站、源码和原始评测记录核验。因此：

- 文章可以证明“有人采用或提出过某种方案”，不能证明本项目已经需要或能够获得相同收益；
- 跨来源重复出现的原则，优先作为讨论候选；
- 平台专属 API、具体架构和实现参数，只作为验证线索；
- 百分比、Token 降幅、准确率、用例数和阈值不直接成为本项目目标；
- 候选应先回答它解决 Harness 的哪个真实问题，再决定进入框架、领域实例或具体能力；
- 单次成功、单次失败或一篇文章不能直接改变稳定系统设计。

## 三、框架级设计候选

以下能力可能跨软件工程、运营、视频生产等领域复用，但是否属于框架核心仍需讨论。

### 全局运行与编排

- 把 Harness 视为模型外的运行层，而不是 Prompt 或 Skill 集合；
- `HARNESS.md` 以全局视角决定子系统何时进入、跳过、交接、回流、验证以及如何汇总当前计算机侧结果；
- HARNESS 管理跨子系统的信息引用、当前有效性和最终汇总，不代替子系统生成内容；
- 对话历史不必自动升级为独立运行状态；只有跨子系统、跨会话恢复或高风险执行确实需要时，才引入
  显式状态、Checkpoint 或更严格的动作校验；
- 短任务应允许只依赖当前对话和业务项目正式资产完成，不承担统一对象模型或状态机成本。

待讨论：当前软件工程实例中，`HARNESS.md` 具体在每一步判断什么、读取什么、把什么交给哪个子系统，
以及何种真实问题出现后才需要把部分语义升级成可执行约束。

### 能力注册与领域实例

- 框架提供领域实例注册接口，不预设固定子系统数量；
- 领域实例声明子系统、能力、依赖、进入条件、跳过条件、产物类型、结果类型和风险门禁；
- 能力可发现、被投影、被加载和实际执行是不同状态，不能因为安装了 Skill 就视为本次任务已启用；
- 横向能力、连接器、领域能力和框架能力需要分开描述；
- 默认装配、项目配置和单任务覆写可以分层，但不能形成不可追溯的隐式变化。

待讨论：领域实例的最小注册合同，以及框架允许领域实例覆盖哪些运行规则。

### 确定性执行边界

- 能由代码判断的权限、路径、Schema、版本、幂等、超时、网络和输出边界，不只依赖模型自律；
- 工具执行前确认目标对象、当前动作、授权范围和副作用；
- 工具执行后记录 Agent 实际观察到的结果；
- 读失败可以在明确边界内降级，写失败和高影响操作默认阻断；
- Hook、Middleware、沙箱和审批 API 是实现候选，不是框架存在的前提。

待讨论：哪些护栏是所有领域共有，哪些必须由领域实例声明；宿主不支持硬拦截时如何降级。

### 演进

- 演进已确认为框架级控制面，不是软件工程领域的最后一个固定阶段；其具体证据与实施合同仍待讨论；
- 领域任务只产生可追溯、可脱敏的运行证据和改进候选；
- 改进需先有问题证据和候选设计；用户决定是否另行启动 Harness 维护任务，再由主会话实施和独立
  验证。Release、发布与回退属于用户授权的仓库维护操作，不由 Retro 自动执行；
- 框架规则、领域设计、Skill、资源、脚本和连接器需要分别找到正确的改进载体；
- 自动发现问题可以探索，自动修改并发布自身不作为当前目标。

待讨论：演进系统消费什么统一证据，哪些改进由框架治理，哪些归领域实例维护。

## 四、整体编排候选

资料共同支持“按任务动态组合”，但并未给出可直接照搬的通用编排模型。目前值得比较三类方案：

### 固定流程

优点是容易理解、审计和回放；缺点是不同任务和领域的摩擦大，容易把“职责存在”误写成“每次必须
执行”。不适合作为 Harness 唯一模型，可以保留为某类领域任务的预设路线。

### 完全由模型动态决定

优点是灵活；缺点是状态、权限、恢复、产物和停止条件容易依赖模型自述，难以稳定验证。不适合承担
高影响执行边界。

### 全局编排与动态能力组合

`HARNESS.md` 管理是否进入意图、知识或路线规划，按路线调度能力、处理反馈与重新规划，并完成最终
汇总；软件工程实例中的 `router` 选择具体能力、顺序、产物要求、测试策略和审计门禁；具体实现负责
完成被选中的能力。初期由宿主 Agent 按运行合同判断，只有恢复、并发、跨会话或高影响操作证明需要
时，才进一步引入形式化状态机或可执行网关。

真实任务仍需校准：

- Router 形成的路线是否足以让 HARNESS 无歧义调度当前能力；
- 能力失败、输入缺失、人工反馈和意图变化能否回到正确负责方；
- 重新规划条件是否既能处理真实变化，又不会让普通执行频繁重算路线；
- 哪些当前产物和证据确实需要跨会话引用，以及变化后需要重新完成哪些计算机侧工作。

## 五、过程产物与结果产物候选

先确认“由谁负责”，暂不强制一套通用对象模型：

| 信息或产物 | 责任方 |
|---|---|
| 当前目标、范围、约束和整体进展 | Harness 维护全局视图 |
| 子系统内部分析及其过程输出 | 对应子系统或 Skill 生成并解释 |
| 跨子系统所需的产物引用、来源、当前有效性和流转关系 | Harness 统一管理 |
| 代码、设计、测试等任务正式资产 | 业务项目在原位置维护，对应能力负责内容 |
| 业务知识、项目核心运行模型、功能知识、数据知识等项目知识 | 知识系统从过程产物和稳定事实中提取，并在业务项目内单独维护 |
| 当前计算机侧结果、验证边界、Agent 实际工具结果和剩余问题 | Harness 面向目标汇总，来源仍归各责任方 |
| 最小运行记录与可脱敏改进证据 | Harness 管理，演进能力按受控流程消费 |

持久化强度由实际消费关系决定：简单任务可以只保留会话上下文；需要跨子系统或跨会话继续时，
Harness 维护轻量的全局进展与引用；需要长期复用、评审或交付的内容进入业务项目正式资产。任何层级
都不要求每个阶段固定生成 Markdown，也不复制一套与业务项目并行的正式文档。

待讨论：软件工程实例在什么条件下提升持久化强度，以及轻量全局视图最少需要记录哪些信息；具体
文件路径、格式和字段尚未确认。

## 六、软件工程领域实例的讨论候选

当前软件工程实例采用五个业务任务职责域；独立交付系统已经移除，演进仍属于 Harness 框架控制面。
其余职责、功能和交接仍需逐个讨论，不能因为现有数量和编号停止校准。

| 当前子系统 | 需要重点讨论的问题 |
|---|---|
| 意图接入 | 何时需要显式形成任务意图；哪些简单任务可以直接确认后执行 |
| 知识 | 代码、项目文档、长期知识和当前任务事实如何分工；何时建设、检索或沉淀 |
| 路由 | 已确认负责具体能力、顺序、稳定产物、测试策略和审计门禁；后续需用真实任务校准风险判断 |
| 执行 | 设计、编码、诊断、测试、修复应如何拆分；哪些是互斥模式，哪些可以组合 |
| 审计 | 何时创建独立 Audit Subagent、审计什么当前差异、如何有限轮次返回反馈和复审 |
| Harness 演进控制面 | 消费哪些运行证据，如何把候选交给用户另行启动的维护任务并验证修改 |

横向 Subagent 还需讨论主会话直接执行、临时 Subagent 与新会话的分派、结果回收和独立验证合同。
人工 Review、风险接受、发布和回退属于用户行为；HARNESS 只约束 Agent 自身的计算机侧外部操作，
`cr` 仅保留为用户主动触发的个人反馈能力，不再作为领域职责或运行节点讨论。

## 七、上下文、Skill 与评测候选

### 上下文

- 采用渐进加载：先判断能力是否相关，再加载核心规则，具体分支需要时读取资源；
- 最小上下文不是少读，而是不传无关全文、旧方案和临时推理；
- 上下文优化需同时观察质量、Token、推理成本、延迟和返工；
- 输入本来短且清晰时，压缩或知识检索应允许不启动。

### Skill

- Skill 可以分为发现信息、核心能力合同和按需资源；
- Skill 只描述自身触发、排他边界、输入、方法、输出、副作用和停止条件；
- 跨能力选择、公共状态、失效传播和授权不放入单个 Skill；
- 真实失败先成为候选，再决定修改触发、正文、资源、脚本或框架规则；
- 候选版本经过代表性 Case 对比后再发布。

### 评测

- 评测对象是模型、Runtime、能力、工具和环境组成的完整运行系统；
- 区分结果正确性、可观察过程、效率成本、鲁棒性安全和人类体验；
- 程序可判断的使用确定性检查，开放性质量使用独立语义审计，高影响标准与风险由人决定；
- Good/Bad Case 和真实失败可以逐步形成回归资产；
- 多 Trial、pass@k、pass^k、LCS 路径比较和评分阈值只在真实任务证明需要后采用；
- 不把隐藏思维链作为公共评测合同或运行证据。

## 八、不直接采用的方案

- 把软件工程当前职责域升级为所有领域必须遵守的框架结构；
- 所有任务固定经过意图、知识、路由、执行、审计和人工确认；
- 每个阶段强制生成固定路径的 Git Markdown 文件；
- 为省 Token 跳过当前文件、权威事实、构建、测试或真实验证；
- 保存全部 Prompt、隐藏思维链或无边界的完整轨迹；
- 让模型或 Skill 自行执行授权、失效传播、发布和回退；
- 业务任务反馈自动改写并立即发布 Harness；
- 把 `build` 设为所有项目首次启用的强制门禁；
- 为项目知识建立版本、敏感信息治理或复杂生命周期状态机；
- 建模、限制或强制用户完成验收、风险接受、发布和回退；
- 为每次请求维护持久化“任务已结束”状态；
- 默认启用长期多 Agent 蜂群、云端多租户、远端 Registry 或动态插件内核；
- 把外部文章的收益数字和评测阈值直接作为本项目标准。

## 九、仍待讨论的边界

当前主运行循环、Router、Coding 和 Audit 的基础边界已经确认；以下内容仍作为后续讨论输入，不代表
实施顺序：

1. Harness 演进控制面消费哪些最小证据，以及如何把候选交给用户另行启动的维护任务；
2. Subagent 作为横向能力时，哪些分派、隔离和独立审计规则属于框架合同；
3. 通过真实任务判断何时需要跨会话引用和当前证据关系，不提前建立通用状态或知识版本模型；
4. 根据宿主能力选择 `HARNESS.md` 的加载、Hook、权限拦截和确定性执行实现。
