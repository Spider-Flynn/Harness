# Router

根据已经对齐的需求、当前项目事实和约束形成需求执行路线。路线说明需要哪些能力、按照什么顺序
执行、哪些结论需要稳定承载、如何获得验证反馈以及是否需要独立审计。HARNESS 消费路线并完成
实际调度；Router 不调用任何能力。

## 输入边界

输入至少应能说明当前目标、范围、验收、保持不变的行为、已知项目事实和可用执行能力。只有缺少的
事实会改变路线时才停止规划，并返回具体事实缺口；HARNESS 可以调用 `intent` 或 `know` 补齐后重新
进入 Router。不要为了完整项目画像要求无关信息。

## 风险维度

只评估会改变执行路线的风险：

- **设计风险**：实现需要新增或改变架构、模块职责、公共契约、数据结构、兼容规则、安全边界，
  或存在多个会实质改变结果的方案。
- **行为风险**：功能包含复杂规则、边界、异常、权限、状态流转、事务、并发或外部副作用。
- **影响风险**：改动跨模块或跨系统，兼容与回退边界、回归范围或验证方式难以直接判断。
- **协作风险**：任务需要跨会话、跨 Agent、多人 Review 或后续长期复用，关键结论不能只留在
  当前对话中。

文件数量、代码行数、是否显式调用某个 Skill，以及形式上的“新功能”或“Bug”标签，不能单独
决定路线。

## 路线决策

### 技术设计

存在设计风险，或当前技术选择、兼容责任、影响范围与回退边界不足以稳定约束实现时，需要先
完成技术设计。目标和需求本身尚未明确不属于技术设计判断。已有适用设计，或修改局部且实现
选择、影响范围和兼容边界已经清楚时，不增加独立技术设计环节。

### 稳定产物

关键设计、行为或测试结论需要跨会话、跨 Agent、多人 Review、独立审计、后续复用或长期维护时，
需要形成独立稳定产物。短小、局部、单会话即可完成且当前对话足以承载全部有效事实时，不要求
额外文档。

这里只决定是否需要稳定产物及其用途，不决定文档名称、结构、模板、内容和保存位置；这些属于对应
执行能力。

### 测试设计

存在复杂行为、多个可观察场景、重要异常与权限边界、状态或副作用，或者回归范围与验证方式
需要先被明确时，需要在实现前完成测试设计。预期单一、边界清楚且已有测试足以表达目标时，
不增加独立测试设计环节。

### TDD 测试先行

当测试能够稳定表达目标行为或复现问题，并且行为复杂、回归风险高、影响多个入口，或者实现
错误代价较高时，选择 TDD，在修改实现前先获得有效失败反馈。

机械修改、简单映射或局部明确调整，已有反馈足以保护行为，或者当前环境无法形成有效失败反馈
时，不强制测试先行。未选择 TDD 只表示不要求先获得失败反馈，不表示可以省略最终验证。

选择 TDD 时，至少需要先明确对应的测试预期；是否形成独立测试设计或文档仍按前述风险判断。
当前信息不足以判断能否形成有效失败反馈时，只把 TDD 作为条件环节：能够形成有效失败反馈时
测试先行，否则不强制，不能直接把 TDD 写成确定路线。

### 根因定位与生产代码修改

错误行为、正确预期或根因尚未证实时，路线先进入 `debug`；根因和修改边界已有证据时可以跳过。
需要新增、修改、修复或重构生产代码时，路线包含代码实现，并由 HARNESS 强制加载 `coding`。Router
不判断是否遵守编码习惯，也不能允许代码修改绕过 `coding`。

### 测试类型

- 没有真实外部入口，或需要穷举复杂内部规则与分支时，选择 `unit-test`。
- 当前需求影响真实 HTTP API 的用户可观察行为时，选择 `it-test` 作为真实入口验证。
- API 内部规则复杂且完整 HTTP 链路也重要时，同时选择 `unit-test` 和 `it-test`。
- 当前入口不是 HTTP，且已有其他适用测试能力时，选择对应能力；缺少能够证明目标行为的能力时，
  返回验证缺口，不用 `unit-test`、Mock 或静态检查冒充真实入口验证。

### 独立审计

实现复杂、影响公共契约或存量行为、安全与权限风险高、修改范围广、验证边界难以判断，或者人工验收
需要独立证据时，路线加入 `audit`。默认在完整候选和验证证据形成后审计；架构、安全、公共契约或
高返工成本设计需要提前核验时，可以在实现前增加设计审计。

Router 决定是否审计、审计对象和所在风险边界，不执行审计，也不定义审计方法。

HARNESS 在稳定结果形成后交回项目知识候选时，Router 将该候选作为独立审计对象加入写入前门禁；
它只确定审计对象和顺序，不判断知识内容、目标结构或写入方法。

## 路线输出

路线以当前任务能够理解的最简形式说明：

1. 依次执行的具体能力及跳过项；
2. 哪些环节需要独立稳定产物；
3. 是否采用 TDD，以及使用什么能力获得失败和最终验证；
4. 是否需要审计、审计什么以及放在哪个位置；
5. 每项选择的风险依据和仍存在的条件环节。

路线不要求固定 JSON、流程文件或七段结构。简单任务保持最短有效路线，复杂任务只增加实际风险需要
的环节。Router 不展开技术设计、文档内容、编码步骤、测试实现和审计方法。

## 重新规划

以下事实出现时，HARNESS 应重新调用 Router：用户目标、范围或验收变化；新事实推翻路线依据；当前
能力证明路线不可执行；实际影响面明显扩大；测试、审计或人工反馈要求增加、删除或重做环节。普通
节点成功后继续原路线，不为每一步重复规划。
