# 项目运行模型建设

## 模型要回答的问题

项目运行模型是当前代码事实的抽象画像。它应让没有阅读具体实现的人理解：

- 项目的边界和主要入口在哪里；
- 项目提供哪些核心能力，这些能力如何协作；
- 哪些核心对象会经历什么状态变化；
- 主要请求、事件和数据怎样完成端到端流转；
- 项目依赖哪些外部系统，失败或中断会影响哪里。

模型描述“项目现在如何运行”，不解释当初为什么选择某个方案，也不罗列类、方法、框架和
代码目录。

## 从代码事实翻译模型

以当前有效的代码、配置、接口、数据库迁移和测试作为可回查基础；存在真实运行证据时，再用于
确认实际行为。先读取项目规则并划定目标仓库、相邻仓库和外部系统的边界；已有 CodeGraph 索引
时按项目规则使用，没有时通过文件与文本搜索定位，不为本次建设自行创建索引。

取证保持只读，不修改生产代码、数据库或外部系统。只有写操作才能验证的行为保留为未验证边界，
不能为了补全模型自行执行。

先盘点入口、定时任务、消息消费、核心对象、状态字段、持久化关系、主要编排和外部集成，形成
“候选能力 → 核心对象 → 入口 → 关键处理 → 数据去向 → 外部依赖”的精简证据地图。不要逐文件
翻译源码，也不要保存与模型结论无关的全量摘录。

静态源码能证明结构和可能路径，测试能证明特定条件下的行为，真实运行证据能证明对应环境和
时间范围内的实际结果。三者的证据等级分别保留，不相互替代。无法到达的路径、来源冲突和尚未
运行验证的行为需要直接标出。

注释、README、目录名称和页面文案只作为定位线索，不能单独证明运行关系。区分活跃实现、停用
实现和尚未接通的能力，不能把“代码存在”写成“系统正在使用”。

## 提炼稳定对象与运行链

用稳定对象、生命周期、完整职责和上下游关系划分能力，不按包、Controller、数据表或页面菜单
划分模块。对每项核心能力至少验证一条代表性运行链，确认：

1. 输入来自谁或哪个系统；
2. 哪个核心对象承载处理；
3. 对象经历哪些关键状态和动作；
4. 哪些环节通过同步调用、异步消息或周期调度连接；
5. 最终形成什么结果，由谁消费；
6. 数据生产、业务编排和动作执行分别属于当前项目还是外部系统。

将已经验证的纵向链路组合为项目整体模型，连接能力之间的供给、消费、触发、回写和反馈关系。
未发现真实调用的候选关系保持为未闭合边界，不为让模型完整而强行连线。

## 表达项目核心画像

根据项目特点选择能力图、对象与状态说明、关键工作流、依赖关系或数据流等表达，不要求每个
项目都具备相同章节。每个关键模型结论都关联到代码、配置、接口或运行证据，使后续能够从画像
回到当前事实核验。

优先沿用项目已有知识入口和文档结构；没有可用载体时，在项目规则允许的位置建立一个可从项目
总入口发现的运行模型载体。按实际模型规模组织内容，不为预设章节创建空文件或空目录。

正文保留项目定位与边界、核心能力、核心对象与生命周期、端到端流程、能力协作、关键数据流和
外部依赖等实际需要的部分。类名、方法名、包路径、表结构、接口清单、搜索过程和建模方法不进入
模型正文；只有技术机制会改变项目责任或运行语义时，才保留必要抽象。

形成候选时说明现有模型、目标位置、待写入模型、事实证据、冲突、未闭合关系和验证边界。通过
知识审计及必要批准后再应用，并重新对照当前项目事实检查。

## 检查模型是否成立

- 每个核心能力都有输入、核心对象、关键处理、输出和上下游；
- 跨能力连接和系统边界都有当前事实支持；
- 能说明主要对象怎样变化、关键数据如何流转以及失败影响哪里；
- 没有把源码目录、页面菜单、接口或表结构直接当成项目模型；
- 没有混入设计方案选择、历史推测和过期路径；
- 静态确认、测试验证和真实运行验证的覆盖范围分别保留。

任一关键链路或边界仍需猜测时，保留未闭合项，不能把该部分标为已建设。
