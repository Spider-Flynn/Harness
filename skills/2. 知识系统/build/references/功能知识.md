# 功能知识建设

## 以功能为知识单元

每个知识单元对应一个需求、功能或模块，服务于理解、使用和后续维护。单元内容按该功能的实际
复杂度选择，通常需要回答：

| 问题 | 记录内容 |
|---|---|
| 为什么有这个功能 | 已确认的功能目标和适用场景 |
| 使用者能观察到什么 | 入口、正常行为、结果和失败表现 |
| 功能遵守什么规则 | 约束、边界、例外和接口契约 |
| 当前方案为什么这样设计 | 已接受的关键设计决定、原因和仍有效取舍 |
| 它与什么协作 | 相关功能及必要依赖关系 |
| 当前可信到什么程度 | 已验证行为、验证方式和未覆盖范围 |

与该功能无关的业务背景不重复收录，类、方法等代码细节只作为回查证据。

## 管理功能状态

已确认需求、正式功能说明、已接受的稳定设计、最终交付结果和可观察行为可以支撑当前功能知识。
讨论中的想法、未接受方案、未完成实现和仅有计划的验证必须保留为候选，不能与当前规则混写。

先划定具体功能边界，再核对需求、稳定设计、最终产物和验证证据是否一致。围绕使用者可见的
行为组织内容，把关键规则和设计决定关联到来源。已有知识、确认需求和当前实现不一致时，分别
记录契约事实、实现事实、冲突及影响，不能只因代码较新就自动覆盖已经确认的功能契约。

沿用已有功能知识入口；没有可用结构时，按实际维护单元选择需求、功能或模块作为导航层级，
建立能从项目知识入口定位的最小载体。不要同时按需求、模块和代码目录维护三套平行分类，也不
为没有稳定知识的功能创建空文件。

功能知识候选需要说明现有内容、目标位置、待写入知识、来源、变化范围、冲突和未验证项；审计
与必要批准完成后才能成为当前功能知识，并再次核对导航、功能契约和实际行为。

## 判断是否可用

功能知识必须让使用者明确知道功能做什么、怎样表现、受什么约束以及哪里尚未验证。稳定设计、
当前行为、验证结果和候选方案的状态应能直接区分，关键事实应能回查到需求、最终产物或验证
证据。只有实现细节的代码说明，或只有目标而没有当前行为与边界的材料，都不算完成建设。
