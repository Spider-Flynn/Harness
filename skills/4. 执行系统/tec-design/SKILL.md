# 技术设计

## 定位

`tec-design` 负责把已确认的目标和必要事实收敛为可实施、内部一致的技术设计。边界清楚的
小改不因缺少独立设计文档而触发；复杂变更可以在当前任务中交付设计结论，也可以形成需要
长期维护的设计和接口契约。

设计遵守一条核心依赖：先确定功能必须表现成什么样，再确认实现依赖的数据事实，最后据此
推导具体流程。不能用后面的实现方案反向补齐前面尚未确认的规则。

本 Skill 不编写需求级测试场景、测试代码或生产代码，也不选择后续 Skill。

## 设计主线

围绕当前变更实际涉及的内容依次收敛：

1. **需求与功能单位**：明确目标、范围及具体功能单位；有接口时形成接口清单。
2. **功能规则**：说明每个功能的行为、限制、适用条件和用户可感知边界，不混入表字段、
   查询顺序或代码实现。
3. **核心数据**：确认稳定的数据结构、核心字段、关联键和关系，只写当前功能真正依赖的内容。
4. **数据源规则**：确认数据的权威来源、业务粒度、唯一性、时间与变化语义、完整性和可用性；
   多源组合时同时确认关联基数、时间对齐以及重复、缺失和未匹配数据的影响。
5. **具体流程**：基于已经确认的功能和数据规则，说明入口、取数范围、校验、判断、转换、
   写入、返回或副作用。异常、兼容、幂等、并发和回退只写在受影响的处理节点，不另行重复展开。
6. **接口契约**：需要独立交付时，保证方法、路径、字段、约束、响应和错误边界与功能、数据及
   流程结论一致；设计正文只保留接口清单和影响方案的关键边界。
7. **待办清单**：无法确认且会影响设计的事实或决策保留为待办，依赖它的方案不能写成确定结论。

这是事实依赖顺序，不是强制交互轮次。已有材料能够支持多个部分时可以一次完成，也不要求每个
部分都扩写成同等篇幅。

## 事实与决策

1. 先读取用户材料和直接相关的文档、代码、DDL、配置或现行契约。新功能不预设存在可复用
   实现；改造现有能力时只沿本次涉及的调用和数据路径确认现状。
2. 区分证据支持的当前事实、已确认目标、合理推测和待决策事项。代码和配置只能证明当前行为，
   不自动代表目标规则；字段名、少量样本或经验不能证明数据语义。
3. 只确认会改变设计选择的信息。能够自行查明的事实直接查明并注明依据；必须由用户决定时，
   集中给出问题、推荐选择、依据及主要影响。
4. 有实质技术取舍时说明最终选择和代价；没有决策差异时不罗列备选方案，不用通用原则扩充篇幅。
5. 修改既有设计时先读完整现行产物，再同步更新受影响的功能、数据、流程、接口和待办。新结论
   直接替换旧结论，最终文档不保留讨论过程或冲突版本。

## 产出与资源

先按当前问题自然组织设计。需要形成稳定设计文档、目标项目没有更权威模板，且统一结构能够
降低遗漏风险时，读取 `assets/technical-design-template.md`。模板中的六部分用于区分规则
职责，不要求平均展开；没有实际内容的可选小节直接删除。

需要单独产出接口契约时，按用途选择：

- Swagger 2.0 JSON：读取 `assets/mock-swagger-template.json` 和
  `references/mock-swagger-template-rules.md`。
- Markdown 接口契约：读取 `references/interface-document-rules.md`。

两种契约同时存在时必须来自同一批已确认事实。文件位置、命名和是否形成独立文档服从当前任务
与目标项目规则。

## 自检

完成前确认：

1. 功能规则、核心数据、数据源规则和具体流程是否按依赖关系形成同一套设计。
2. 同一事实是否只在所属部分完整说明，其他位置没有重复扩写。
3. 数据和接口结论是否有依据，未确认事项是否仍明确保留为待办。
4. 是否只保留会影响实现的规则、数据和决策，没有为了结构完整增加内容。
5. 修改既有设计时，所有受影响内容是否一致更新。
6. 是否越界编写了测试场景、测试实现、生产代码或外部流程编排。
