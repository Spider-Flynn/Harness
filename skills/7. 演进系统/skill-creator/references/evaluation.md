# Skill 创建评测

只在 `SKILL.md` 指定的条件成立时读取本文件。目标是证明新 Skill 在真实任务中产生可辨认
价值，并发现误触发、过拟合和无效规则；不是让每次创建都运行完整基准。

## 先定义要证明什么

按风险选择证据，不混用结论：

| 风险 | 最小证据 |
| --- | --- |
| 结构或资源错误 | frontmatter、元数据、路径和脚本静态校验 |
| 触发过宽或过窄 | 隔离上下文中的正向、隐含表达、近似反例和停止场景 |
| 确定性产物错误 | 可重复检查的结果断言或验证脚本 |
| 主观质量不足 | 用户基于真实输出进行定性评审 |
| Skill 是否真正增益 | 相同输入下的有 Skill 与无 Skill 基线比较 |
| 两种实现谁更好 | 隐去来源的盲比，再分析差异产生机制 |
| 行为存在随机波动 | 对少量关键用例重复运行并报告波动，不用单次结果定论 |

静态结构通过不能证明行为有效；一次行为成功也不能证明触发稳定或普遍增益。
仓库中的路由数据只记录静态契约，不替代隔离上下文中的模型行为验证；Prompt 行为也不通过
`tests/test_<skill>.py` 模拟。

## 设计真实用例

用例来自真实使用方式，至少覆盖：

1. 用户直接表达目标的正向场景。
2. 不点名 Skill、但意图明确的隐含场景。
3. 缺少关键输入时应询问或停止的场景。
4. 与相邻能力共享词语、但不应触发的近似反例。
5. 最容易暴露脆弱步骤、错误推断或输出缺陷的边界场景。

不要用与能力明显无关的负例制造虚假的高通过率。主观验收标准由用户确认；可确定性检查的
结果优先写成脚本或明确断言。

## 保护评测独立性

- 有 Skill 和基线使用相同任务、输入文件、权限与环境；新 Skill 的基线是不加载该 Skill。
- 验证者只接收任务和待验证产物，不接收预期答案、问题诊断、拟修改规则或创建过程。
- 产物写入隔离目录；下一轮开始前避免让执行者读取上一轮输出和分析。
- 主观比较先隐藏版本来源，完成判断后再读取 Skill 和执行轨迹解释原因。
- 用户未授权 Subagent、外部系统或高成本运行时，使用当前会话完成最小验证并说明独立性边界。

## 评估增益而非堆指标

断言应区分 Skill 带来的真实价值。检查：

- 是否在有 Skill 时稳定通过、无 Skill 时经常失败；两边都通过的断言通常不能证明增益。
- Skill 是否增加无效步骤、耗时、Token 或工具调用，成本是否换来了需要的质量提升。
- 失败来自 Skill 规则、执行偏差、环境阻断还是用例本身不可靠。
- 修改建议是否能泛化到其他真实任务，而不是只修当前用例。

不要根据总分自动改写 Skill。先确认失败机制，再决定修改正文、description、资源、脚本，
或者承认 Skill 没有带来足够价值。

## description 专项评测

只有主要风险是触发边界时才做专项评测：

1. 准备覆盖不同措辞的正向用例，以及与相邻 Skill 竞争的近似负例。
2. 将一部分边界用例留作最终检查，不参与 description 调整。
3. 根据误触发和漏触发修改职责、触发条件或排他边界，不堆叠关键词。
4. 用留出用例复核，避免只对已知问题拟合。

当前平台没有可验证的自动触发测试入口时，把路由 JSON 视为静态契约，不宣称模型真实触发
已经通过。

## 产物与结论

只有后续确实需要复查、比较或重复运行时才保存评测产物。推荐最小记录包含：

- 用例、输入和验收条件。
- 使用的 Skill 版本或基线条件。
- 实际输出、断言证据和必要的耗时或调用数据。
- 已确认失败机制、用户反馈和未验证事项。

最终结论分别说明结构、路由契约、行为质量和真实增益，不用一个“评测通过”覆盖所有证据
边界。
