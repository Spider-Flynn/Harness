# Build

## 定位与共享规则

Build 组织一次用户主动发起的知识建设对话，按本次范围形成可维护的知识资产。它不是接入门禁，
不要求首次建设全部类型，也不把四类知识变成四场互相重复的访谈。

先读取目标项目规则，并加载只读依赖 `.agents/skills/rules-know/SKILL.md`，按建设对象读取共同规则
和命中类型规则，而不是按材料格式选择。内容结构、目录、索引、模板与质量由该依赖统一维护，
本 Skill 继续负责来源问答、知识建设和回读，不复制规则或把依赖变成独立流程。
依赖入口缺失时报告接入缺口，由主会话处理，不在目标项目临时发明另一套规范。

## 先确认信息源

1. 先向用户索取或确认本次已有的信息源：说明材料、业务文档、流程图、接口材料、数据结构、样本或
   用户口述。用户已经明确提供的直接使用，不重复索要；不能因为身处存量项目就默认读代码。
2. 确认本次想建设的范围，并读取用户指定材料与已有目标知识，形成当前理解。已有知识是更新基线，
   不能把其中未确认内容自动当成事实。
3. 信息不足时先围绕缺口追问或请求补充材料。只有这些方式仍不能解决关键缺口，才说明要读取哪些
   代码、解决什么问题，并在用户同意后按最小范围读取；不能自行扩大为全库扫描或运行系统。

新项目和存量项目遵循同一采集顺序。新项目主要记录业务画像、已确认目标与方案，不把未实现设计
描述成当前运行事实；存量项目先使用提供的来源，只有必要且获准时用代码核对尚不清楚的局部关系。
用户没有更多材料且不同意读代码时，交付已能确认的知识和缺口，不以猜测补齐。

## 连续问答与分批建设

- 每轮围绕一个认知主题，先给出有来源支持的当前理解，再询问会影响结论的缺口；问题说明为什么
  需要回答，可给出建议或选项，但不替用户决定业务事实。
- 已经明确的信息不重复确认，代码或材料能直接证明的事实不逐条要求用户背书；跨来源矛盾与影响
  业务含义的推断要指出并确认。一个回答影响多类知识时复用同一次确认，不重复采访。
- 随材料、回答和纠正调整下一问，不把轻模板变成必须逐项填完的问卷。只要本次主题已经可解释、
  有来源且边界清楚，就可以形成该主题的候选；不等待全部知识类型齐全。
- 过程理解保留在当前对话即可；跨会话确需继续时，按 Runtime 的产物规则保存必要引用与待确认项，
  不保存全量聊天或另建任务状态机。

## 形成、应用与交回结果

依据共享规范比较现有知识，形成拟新增或更新的内容、位置、来源和仍未解决的事项。由主会话按
Runtime 判断当前授权和所需门禁；Build 不自行调用 Router 或 Audit，也不设额外的强制知识审计。
需要补充裁决、审计或写入授权时先返回候选；已满足本次所需条件时，按共享维护规则应用并回读。

返回实际知识位置与覆盖范围、已应用变化或尚待处理的候选，以及会影响使用的缺口。质量以对应类型
规则为准，不以文件数量或四类是否全部建完为准；完成本次建设后停止，不自动进入需求开发或提交发布。
