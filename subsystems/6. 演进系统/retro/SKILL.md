# Retro

`retro` 只复盘 Harness 本身。它根据已确认目标、真实执行轨迹和最终结果判断 Harness 是否可靠地完成任务，并提出可实施、可验证、可回退的改进候选。它不自行定义业务产物的好坏，不替代项目知识沉淀，也不修改 Skill、规则、Agent、工具或门禁。

## 判断是否具备复盘条件

仅在任务结束后复盘。先确认输入能还原以下三类事实：

- **预期**：已确认目标、验收标准、约束、授权和适用规则；
- **轨迹**：实际使用的信息源、能力和工具，以及关键交接、人工介入、返工、失败与恢复；
- **结果**：最终稳定产物、真实验证、审计与人工决定，以及可核验的外部状态变化。

只读取复核问题所需的轨迹，不要求记录或复述完整推理过程。会话中的模型自述、文件存在、静态检查或 Mock 结果只能证明各自范围，不能替代真实结果和外部状态。

缺少任一关键事实且会改变判断时，返回仍有效事实、缺失证据和可继续复盘的条件，不形成问题结论或改进候选。单次运行只能证明本次表现；没有可比运行时，不推断稳定性趋势或普遍效率问题。

## 建立本次评测标准

从本次任务的已确认目标和验收标准中提取少量关键断言，能明确判断时使用“满足 / 不满足 / 未知”，并为每项结论绑定证据。`未知` 表示证据或标准不足，不等同于失败。

按以下四层检查，不为目录完整而堆叠指标：

1. **结果**：任务是否按已确认验收完成，实际外部状态是否与交付声明一致。
2. **过程**：能力选择、工具调用、关键交接、失败处理和验证路径是否正确、可复核，结果是否依赖偶然命中或未说明的人工补救。
3. **效率**：耗时、Token、工具调用、上下文加载、人工介入和返工是否存在有证据的不必要成本。
4. **风险**：是否遵守权限、隔离、审计、外部操作和证据边界，是否存在越权、误操作或未经验证的结论。

业务结果只按用户确认的标准、真实验证、审计与人工决定判断；不得由 `retro` 另造业务评分标准。标准本身不清楚时，将其列为缺失条件或观察项。

## 还原问题与归因

按时间顺序还原影响结论的最小执行轨迹，对照预期行为与实际行为，定位最早出现偏差或风险证据的位置。先描述可观察事实和影响，再判断造成偏差的机制，不用最终结果反推未经证实的过程。

归因时区分 Harness 的规则、Skill、能力选择、上下文与证据交接、工具或环境约束，以及一次性项目事实、人工执行偏差和模型波动。只有证据能够说明 Harness 机制导致问题或未能约束可预见风险时，才形成 Harness 问题结论；其他情况保留为观察项，并说明需要什么证据才能继续判断。

## 形成改进候选

仅当以下条件同时成立时提出候选：

- 已有证据表明实际行为偏离预期或造成不必要风险、返工或成本；
- 问题与某个 Harness 机制之间存在可说明的关系；
- 期望行为具有复用价值，不只是当前项目事实、一次性偏好或偶发环境故障；
- 能说明改进后的验证方式和失败时的回退方向。

重复出现的同类问题优先形成候选；单次问题只有在正确性、安全、权限或不可逆影响足够高且证据充分时，才可直接提出候选。证据只能支持继续观察或补充验证时，不用建议包装成已成立的系统问题。

## 输出复盘报告

输出的 Harness 复盘报告至少包含：

- **范围与依据**：任务范围、预期行为、所用证据、缺失证据和本次结论边界；
- **分层评测**：结果、过程、效率、风险中的关键断言、结论和证据；
- **已证实发现**：实际行为、影响、最早偏差位置、归因依据和仍存在的不确定性；
- **观察项**：尚不能归因的现象、未覆盖范围和继续判断所需证据；
- **改进候选**：目标行为、问题证据、作用机制与范围、最小改进方向、验证场景、风险和回退方向。

没有可证实系统问题时，仍输出证据范围和分层结论，不为凑改进而提出候选。发现值得保留的代表性成功或失败场景时，可以建议将其转为后续回归 Case，但不在本能力内建设 Case 库或自动回归机制。

## 改进边界

复盘只解释证据并提出候选，不定义整体演进编排，不自动修改任何 Skill、规则、Agent、脚本或其他 Harness 产物，也不直接启动维护、评测基建或发布门禁建设。

改进候选交给用户决定是否另行启动 Harness 维护任务；该任务负责实际修改、验证和必要记录，
发布与回退由用户决定。Retro 在返回复盘报告和候选后完成本次工作。
