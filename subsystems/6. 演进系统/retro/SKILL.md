# Retro

`retro` 是投影到业务项目的 Harness 自身复盘演进能力。它在独立新会话中启动，避免污染原任务会话；根据已确认目标、任务产物、运行事件轨迹（及原会话转录）和最终结果，复盘 Harness 是否可靠完成任务。**Retro 不应该只做问题分析，分析后必须给出具体答案与可执行方案**（如优化现有 Skill、调整编排、创建新 Skill 或增加确定性机制），坚持以最小代价解决问题，严守架构分层，防范规则混乱与系统腐化（“不成屎山、结构清晰”）。

## 运行形态与触发机制

Retro 必须在**独立新会话**中运行，两会话完全解耦、无需交互。支持两种触发途径：

1. **用户主动新会话触发**：用户自行新开会话，提示词中指定原任务会话信息（会话 ID 或转录）以及目标任务目录 `.harness/tasks/YYYYMMDD-任务简名/`（包含产物文档与 `events.jsonl`），调用 `retro` 执行复盘。
2. **AI 主动提议 + 会话派生/注入（审计完成或任务交付后）**：任务结束或审计通过后，若 HARNESS 观察到显著系统摩擦（或用户要求复盘），主动向用户提议；用户确认后，当前业务会话创建新会话（若宿主支持）或生成注入提示词（明确包含会话 ID、任务目录路径、产物文件清单及调用 `retro` 指引），由新会话独立接管并完成全部后续工作。

## 输入与输出载体

- **输入来源**：
  - 目标任务目录 `.harness/tasks/YYYYMMDD-任务简名/` 下的各类稳定过程产物（`spec.md`、`测试设计.md`、`测试结果.md`、`审计报告.md` 等）；
  - 任务目录下的极简运行事件轨迹 `events.jsonl`（包含能力流转、重跑返工、Audit 协商轮次与结论等关键事实）；
  - 原任务会话信息（会话 ID 或转录，用于辅助核对实际交互与上下文；若宿主无法提供跨会话转录，以前两项为不可退缩的第一基线，不阻断复盘）。
- **输出载体**：复盘报告与演进方案统一输出到对应任务目录下的 `retro.md`（`.harness/tasks/YYYYMMDD-任务简名/retro.md`）。

## 判断是否具备复盘条件

仅在任务结束后复盘。先确认输入能还原以下三类事实：

- **预期**：已确认目标、验收标准、约束、授权和适用规则；
- **轨迹**：实际使用的信息源、能力和工具，以及关键交接、人工介入、返工、失败与恢复；
- **结果**：最终稳定产物、真实验证、审计与人工决定，以及可核验的外部状态变化。

只读取复核问题所需的轨迹，不要求记录或复述完整推理过程。会话中的模型自述、文件存在、静态检查或 Mock 结果只能证明各自范围，不能替代真实结果和外部状态。

缺少任一关键事实且会改变判断时，返回仍有效事实、缺失证据和可继续复盘的条件，不形成问题结论或改进候选。单次运行只能证明本次表现；没有可比运行时，不推断稳定性趋势或普遍效率问题。

## 建立本次评测标准

从本次任务的已确认目标和验收标准中提取少量关键断言，能明确判断时使用“满足 / 不满足 / 未知”，并为每项结论绑定证据。`未知` 表示证据或标准不足，不等同于失败。

按以下四层检查，不为目录完整而堆叠指标：

1. **结果**：任务是否按已确认验收完成，实际外部状态是否与交付声明一致。
2. **过程**：能力选择、工具调用、关键交接、失败处理和验证路径是否正确、可复核，结果是否依赖偶然命中或未说明的人工补救。
3. **效率**：耗时、Token、工具调用、上下文加载、人工介入和返工是否存在有证据的不必要成本。
4. **风险**：是否遵守权限、隔离、审计、外部操作和证据边界，是否存在越权、误操作或未经验证的结论。

业务结果只按用户确认的标准、真实验证、审计与人工决定判断；不得由 `retro` 另造业务评分标准。标准本身不清楚时，将其列为缺失条件或观察项。

## 还原问题与归因

按时间顺序还原影响结论的最小执行轨迹，对照预期行为与实际行为，定位最早出现偏差或风险证据的位置。先描述可观察事实和影响，再判断造成偏差的机制，不用最终结果反推未经证实的过程。

归因时区分 Harness 的规则、Skill、能力选择、上下文与证据交接、工具或环境约束，以及一次性项目事实、人工执行偏差和模型波动。只有证据能够说明 Harness 机制导致问题或未能约束可预见风险时，才形成 Harness 问题结论；其他情况保留为观察项，并说明需要什么证据才能继续判断。

## 形成演进答案与落地方案

Retro 严禁停留在空泛的问题描述或方向建议；**分析完问题后必须直接给出明确的演进答案**。演进答案必须秉持**最小代价解决问题、防范系统腐化（结构清晰、不成屎山）**的原则：

1. **四类具体解法**：
   - **优化现有 Skill**：精准定位到具体 Skill 的具体文件、段落或规则，消除歧义、补齐约束或消除潜在死循环（成本最小，优先推荐）；
   - **调整编排机制**：在 Router 规划条件或 HARNESS 运行循环中调整能力准入、跳过或前置依赖，解决时序或路线摩擦；
   - **新建独立能力**：仅当问题属于全新职责域且无法在现有子系统中自洽承接时，设计新 Skill（按框架规范定义边界、输入输出与资源）；
   - **增加确定性防护**：若问题可通过静态检查、Hook 或脚本拦截，优先增加代码级门禁，不盲目依赖 Prompt 约束。
2. **防腐化与防混乱原则**：
   - 严守系统分层（框架层 vs 领域实例层 vs 具体实现），不在底层打补丁掩盖顶层设计缺口；
   - 不增加平行冲突规则，不制造一次性特判逻辑，不把单次现象沉淀为系统级负担，保持整体架构自洽精简。

## 输出复盘与演进报告

报告统一输出到当前任务目录下的 `retro.md`，至少包含：

- **范围与依据**：任务范围、预期行为、所用证据（产物、events.jsonl、会话记录）与本次结论边界；
- **分层评测**：结果、过程、效率、风险中的关键断言、结论和证据；
- **已证实发现**：实际行为、偏差事实、最早偏差位置、归因机制与仍存在的不确定性；
- **明确演进答案**：
  - 拟采取的解法类别（优化 Skill / 调编排 / 建能力 / 加机制）；
  - 具体涉及的文件与改动草案（精确到行或规则点）；
  - 为什么这是最小代价方案，如何确保系统不碎片化、结构清晰；
  - 演进后的验证场景与失败回退方案。

## 闭环演进落地

Retro 输出带有明确演进答案的 `retro.md` 后，交给用户审阅并拍板：
- 若用户不打算采纳，复盘在此结束；
- 若用户确认采纳该方案，主会话直接在**当前新会话中**无缝执行修改（针对既有 Skill 可参考 `skill-neat`，针对新建能力可参考 `skill-creator`，或直接执行框架修改与验证）；
- 落地修改与验证结果记录到 Harness 仓库的 `docs/演进记录.md`。Release、发布与回退由用户决定。
