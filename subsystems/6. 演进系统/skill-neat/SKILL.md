# Skill Neat

## 定位

负责已有 Skill 的完整迭代，不把维护窄化为追加文字规则。根据实际问题调整真正承载能力契约的触发描述、正文、元数据、资源、脚本或其他组成部分。

以用户确认的期望结果和最终约束为准，同时承担 Skill 内部规则系统的 owner 职责：理解输入、发现根本问题、选择抽象层级、维护整体一致性和长期可维护性。用户提供的任何信息，包括措辞完整的规则，都先作为需求和证据处理，不天然是可以直接写入 Skill 的最终规则。

从想法到首次创建验收使用 `skill-creator`，不能因为目录或 `SKILL.md` 已经生成就提前切换。
完成首次创建并进入维护状态后，按需使用其格式和基础校验要求迭代已有 Skill，并遵守目标
位置的现行规则；不要把这些外部约束复制进本 Skill。

## 核心原则

1. 先解决用户真正遇到的问题，再决定如何表达规则。不要把用户的词语、分类或建议方案直接升级为 Skill 结构。
2. 先用正向的上位原则说明同类行为最终应当怎样。只有条件确实改变结论时才增加条件规则，只有当前内容存在真实歧义、风险或例外时才补充负面规则。
3. 先理解完整 Skill，再修改承担该职责的现有内容。优先修改、合并、删除和移动，不以新增标题、段落或清单为默认动作。
4. 每次迭代都同时控制规则熵和加载成本。新内容必须带来必要的行为差异或表达精度，不能留下重复职责、平行分类、冲突标准、历史案例残片或只相对旧版本成立的孤立规则；详细非核心知识按需下沉到引用资源，不让正文持续膨胀。
5. 根据根本机制和执行风险选择正确载体与自由度。多种做法都成立时保留原则，脆弱、重复或需要确定结果的步骤优先进入脚本；资源或元数据问题不强行改写成正文规则，局部事实也不能污染通用触发和默认行为。
6. 保留不确定性并让验证结论服从证据。静态一致、路由契约、脚本结果和真实行为分别只证明对应范围。

## 输入与事实来源

先读取目标 Skill 的完整 `SKILL.md`，再按实际影响补充必要材料：

1. 用户本轮提供的信息，以及相关失败输出、会话、diff、日志或其他原始证据。
2. 与目标行为直接相关的元数据、资源、脚本、模板和测试。
3. 直接影响目标 Skill 的上游入口、下游协作方和适用的项目规则。
4. 当前修改需要遵守的官方格式和现有校验工具。

不要只读取命中用户关键词的局部段落，也不要为了显得完整加载无关材料。

## 迭代流程

### 1. 还原真实问题

无论用户给出的是直接规则、模糊要求、具体案例、模糊案例、失败现象还是建议方案，都先还原：

- 用户真正要改变的结果，以及否定针对的是目标行为、现有约束、表达方式还是适用范围。
- 当前可观察的行为、问题和成本。
- 已确认事实、用户判断、建议方案与尚未证实的推测。
- 当前表达背后的共同约束，以及信息不足时仍需确认的关键边界。

先回答“问题为什么发生、什么变化才算解决”，不要直接回答“用户这句话应写进哪里”。删除
一项约束只表示不再由它限制，不等于建立相反约束；只有用户期望或其他事实明确要求相反
行为时，才改写为反向规则。用户给出的实现方式可能正确，也可能只是局部解法；必须独立
判断并说明依据。

### 2. 定位产生问题的机制

从目标 Skill 的实际执行链路判断问题来自哪里：

- 规则缺失、表达歧义、抽象层级错误或多条规则组合造成的行为。
- 触发、元数据、资源、脚本或协作边界与正文不一致。
- 原有内容已经正确，但执行、验证或外部事实存在问题。

没有证据证明规则导致问题时，不要为了回应反馈强行修改规则。

### 3. 建立最小规则层级

按以下顺序组织候选规则：

1. **整体原则**：先用一条上位约束覆盖所有本质相同的行为。能够一句话统一约束时，不按案例中的角色、层级、步骤或术语拆成多个场景。
2. **条件规则**：只有某个稳定条件会改变要求时，才单独写成“当……时必须/禁止……”。条件描述业务或能力差异，不复刻案例表面结构。
3. **例外边界**：只有整体原则确实不适用时才声明例外，并说明失效条件；不要用例外反向定义主规则。
4. **示例**：只在明显降低理解成本时保留，不让示例承担规则职责，也不把示例名词变成固定分类。

使用相似场景和合理反例检查抽象：换掉用户案例中的对象和措辞后仍能解决同类问题，同时不会约束本不该覆盖的行为。

### 4. 审计完整规则系统

把候选原则放回完整 Skill，检查：

- 是否已有规则承担相同或更上位的职责。
- 新旧规则是否重复、冲突、互相覆盖或形成双重标准。
- 同一原则是否散落在多个章节，能否合并成一个事实来源。
- 条件、例外和示例是否混进整体原则，造成无意义的平行分类。
- 触发、正文、元数据、资源、脚本及协作边界是否相互一致。
- 修复是否引入额外交互、上下文、执行或验证成本。

逐项决定修改、合并、删除、移动、保持或确有必要时新增；不得默认现有章节正确，也不得默认新增内容必须拥有独立位置。

### 5. 形成最小完整修改

1. 先改承担该职责的现有内容。删除或替换一项内容时，同步清理只依赖它成立的说明、禁令、例外、引用和验证，不留下语义孤儿。
2. 只有没有合适载体时才新增内容；只有职责确实独立时才新增章节。
3. 触发范围变化时才修改 description，用户入口变化时才修改界面元数据，产物或执行机制变化时才修改对应资源和脚本。
4. 多个 Skills 真正共享同一契约时才协同修改，不把单 Skill 问题扩大成全套治理。
5. 保留仍然有效的事实，正式规则只描述最终能力，不记录本次聊天、修复轨迹、旧版本解释或新旧方案对比。

存在会改变结果的实质判断时，编辑前向用户说明根本问题、推荐原则、适用边界、规则关系、
验收标准和验证方式。用户已经明确要求执行或确认过同一方案时，直接继续。

### 6. 以最终 Skill 做隔离审计

形成候选结果后，暂时丢弃用户反馈、旧版本、diff 和本轮修改理由，只读取最终 Skill 及其
现行资源，模拟一个完全不了解迭代过程的新会话重新审视：

- 能否独立理解触发条件、目标、执行方式和条件边界，以及实际存在的产物与验收契约。
- 每句话是否仍有当前存在的约束对象，并实际影响行为；只用于解释本轮修改、对比旧版本或
  禁止已删除内容的句子直接删除。
- 正文是否以命令式正面说明最终行为；只有确需区分角色时才明确执行主体，只有当前仍存在
  歧义、风险或例外时才保留负面规则。
- 多条内容能否由一条更上位且准确的规则替代；条件分支是否真的改变行为；是否仍有同义
  重复、术语漂移、职责交叉、前后冲突、失效规则或无必要价值的复杂度。

发现问题就继续合并、改写或删除。隔离审计只评价最终 Skill 是否独立、清楚和必要，不以
diff 更短、删除文件更多或静态校验通过代替语义质量。

## 验证边界

根据实际变更选择最小充分证据：

- 仅向验证者提供最终 Skill 及其现行资源，检查在不知道用户反馈、旧版本和预期结论时能否
  正确理解；无法使用独立验证者时，由当前会话按相同信息边界完成假想验证并说明边界。
- 用原始问题确认新规则能阻止同类失败，不只检查是否出现了新增关键词。
- 用不同措辞的相似场景确认规则没有绑定当前案例。
- 用合理反例确认整体原则、条件和例外没有过度泛化。
- 运行目标位置已有的格式、路由、脚本或行为校验；没有对应设施时不要虚构结果。

静态检查只能证明结构和契约，不能证明真实行为。行为验证未执行、失败或只覆盖局部时如实说明，不反复追加验证制造“通过”。

## 完成要求

完成前确认：

1. 只读取最终 Skill 及其现行资源时，仍能独立理解并执行完整能力。
2. 根本约束已由整体原则和必要条件表达，没有绑定单一案例或形成过度泛化。
3. 触发、正文、元数据、资源、脚本和直接协作契约一致，不存在重复、冲突、过程残留或
   只相对旧版本成立的内容。
4. 原始问题、相似场景和合理反例均已检查，验证方式与结论边界一致。
5. 完成当前任务及目标位置明确要求的验证和直接关联维护；没有相应规则时不自行扩大范围。

最终只说明实际变化、抽象出的核心原则、验证证据和未验证事项，不重复完整迭代过程。
