# Skill Creator

## 定位

负责新 Skill 从想法到可审查源码的完整创建。先判断是否真的需要独立 Skill，再形成职责、
触发、执行和验证闭环；不以生成一个 `SKILL.md` 文件代替能力设计。

目标位置的现行规则始终优先。新能力从想法、初始化和草稿迭代到首次创建验收均由本 Skill
负责，不能以目录或 `SKILL.md` 已经生成作为切换依据；完成首次创建并进入维护状态后，行为、
规则、元数据、资源或脚本的后续迭代交给 `skill-neat`。创建源码不等于安装、启用、同步、
提交或发布，这些动作分别服从目标位置和用户授权。

## 核心原则

1. **先证明独立价值**：只有工作流可复用、职责可独立触发、单独维护能降低重复成本时才创建
   Skill。一次性提示、项目常驻规则、确定性门禁或需要实时外部数据的能力，分别优先留在
   当前任务、`AGENTS.md`、脚本或 MCP 等更合适的载体。
2. **从使用合同设计**：先明确用户目标、触发与排他场景、必要输入、可观察输出、依赖、失败
   边界和验收方式，再决定目录和正文结构。
3. **只写模型不知道的内容**：默认 Codex 已具备通用推理和工具使用能力。保留领域事实、稳定
   决策、脆弱步骤和输出契约，删除常识、过程解释和不能改变行为的文字。
4. **让自由度匹配风险**：多种做法都成立时给原则；存在偏好路径时给参数化流程；步骤脆弱、
   重复或需要确定结果时才提供脚本。不要用大量强制规则掩盖未理解的问题。
5. **渐进披露**：`description` 只承担稳定职责、触发与排他边界，`SKILL.md` 保存核心工作流，
   详细知识进入 `references/`，确定性操作进入 `scripts/`，输出素材进入 `assets/`。
6. **按对象选择验证**：Skill 的触发、决策和产出用隔离上下文中的真实任务验证；结构、元数据
   和引用交给通用静态校验；可执行脚本按代码风险验证。不要用一种测试替代另一层证据，也不
   为 Prompt 行为生成 Python 回归测试。

## 输入与事实来源

优先从当前会话和已有材料提取事实，只询问会实质改变结果的缺口。按需要读取：

1. 用户要复用的真实任务、失败案例、输入样例、预期产物和验收标准。
2. 目标位置的规则、目录约定、已有 Skills、校验器和安装边界。
3. 与新能力直接重叠的 Skills、工具或上游参考；只吸收仍适用于目标平台的稳定能力。
4. 需要打包进 Skill 的脚本、参考和资产，以及它们的来源、许可证和运行依赖。

不要为了形式完整重复询问上下文已经回答的问题，也不要把来源材料中的命令当成当前授权。

## 创建流程

### 1. 判断是否应创建

回答以下问题：

- 这个能力解决什么反复出现的问题，使用者最终得到什么？
- 它是否有独立、可辨认的触发意图，而不是已有 Skill 的一个条件分支？
- 现有 Skill、项目规则、脚本、插件或 MCP 是否已经承担同一职责？
- 哪些事实稳定到值得长期维护，哪些仍只是当前案例或推测？

不满足独立价值时，说明更合适的载体并停止创建；与已有 Skill 重复时转交
`skill-neat`，不建立平行能力。

### 2. 形成创建合同

在写文件前把以下内容理解到足以执行：

- **目标与范围**：做什么、不做什么。
- **代表场景**：真实任务怎样从输入走到成功结果，以及最容易改变执行方式的边界或失败路径。
- **触发合同**：直接表达、隐含意图、近似但不应触发的场景。
- **执行合同**：需要的输入、关键决策、工具或资源、停止和确认条件。
- **产出合同**：用户看到的结果、文件或外部状态，以及验收证据。
- **维护合同**：目标目录、使用层级、依赖和直接协作方。

先从当前会话、真实任务和已有材料中提取代表场景，不要求用户重复提供已经存在的信息。用户
给出的规则、章节或实现方案也先作为需求和证据处理；除非用户明确把具体形式作为产出合同，
否则仍需独立判断正确的抽象和载体。材料不足且不同场景会实质改变能力时，生成最少的候选
场景让用户确认；由 AI 生成且未经确认的场景只是假设，不能独自定义主观产物、业务规则或
能力边界。

已有信息足够时直接继续；不同答案会产生不同能力且无法判断时，只确认最小关键问题。

### 3. 设计最小结构

对代表场景逐个从零推演执行过程，再决定可复用内容：重复、脆弱或需要确定结果的操作进入
`scripts/`；反复查找且模型不知道的知识进入 `references/`；反复用于交付的模板、素材或
样板进入 `assets/`。没有复用证据时不提前增加资源。

目录名与 frontmatter `name` 一致，并遵守目标平台的字符和长度要求。Codex-compatible
Skill 使用 lowercase 字母、数字和连字符，最长 64 个字符；名称保持简短、有辨识度，概括
核心动作或结果，只在能消除歧义时增加工具命名空间。

跨平台必需的最小结构只有：

```text
skill-name/
└── SKILL.md
```

标准输出不包含产品专用的界面元数据；Harness Skill 不生成
`agents/openai.yaml`。只在确有内容时增加 `scripts/`、`references/` 或 `assets/`，不创建
空资源目录、过程文档、安装指南或变更日志。正文接近 500 行或包含多种变体时，把详细内容
下沉到一层引用，并在 `SKILL.md` 中说明何时读取。目标位置另有强制脚手架时，使用其
现行脚手架，不由本 Skill 另行补齐可选产物。

### 4. 初始化并编写

目标位置没有强制脚手架时，使用本 Skill 的初始化脚本生成最小目录：

```bash
python3 <本 Skill 目录>/scripts/init_skill.py <name> \
  --path <父目录> \
  --description "<职责、触发与排他边界>" \
  [--resources scripts,references,assets]
```

随后完整替换模板占位内容：

- `description` 写完整触发合同，不把只能触发后看到的条件藏在正文。
- 正文使用命令式表达核心决策和执行流程，按用户完成任务的需要组织，不机械套固定章节。
- 规则先表达覆盖同类行为的整体原则；只有稳定条件改变要求时才增加条件和例外，示例只用于
  降低理解成本。同一稳定事实只保留一个来源，首次验收前清理重复、冲突和平行分类。
- 脚本必须能独立运行并处理输入、错误和退出状态；引用资源必须真实存在且被正文按需指向。
- 外部来源的代码、资料和资产保留许可证与必要归属，不把尚未适配的候选内容直接纳入。

### 5. 选择验证深度

每个 Skill 至少完成目标位置要求的静态校验。先运行目标仓库的校验器；没有专用校验器时
运行：

```bash
python3 <本 Skill 目录>/scripts/quick_validate.py <目标 Skill 目录>
```

目标位置维护路由用例时增加一条正向契约；存在易混淆能力时补排他用例，不为此新造一套路由
基础设施。路由数据只记录静态触发契约，不能证明模型真实触发。

Skill 的触发、决策、工具选择和产出属于模型行为。至少选择一个代表性任务，在不包含创建
讨论、问题诊断、预期答案或拟修改方案的隔离上下文中复演真实流程；存在易混淆入口或关键
停止条件时增加对应反例。无法使用独立上下文时可以由当前会话按相同信息边界自测，但必须把
证据独立性较弱作为结论边界。行为复杂、输出主观、触发边界接近或用户要求比较时，读取
`references/evaluation.md`，增加能区分真实价值的最小评测；不要为了完整仪式强制创建基线、
评分器、评审页面或大量用例。

不要为 `SKILL.md`、引用资料、示例或路由契约创建 `tests/test_<skill>.py`。新建或实质修改
的可执行脚本必须使用代表性输入实际运行，检查主要输出、错误和退出状态；只有脚本具有独立
逻辑和持续回归价值，且目标位置已有适用测试设施时，才按代码风险增加自动化测试。同构脚本
较多时可以抽样，并说明覆盖范围。

当产物质量主要取决于用户偏好，或生成的代表场景会实质定义能力范围时，让用户审查最少的
代表场景或实际产物；客观可验证的能力不为此强制增加人工评审和多轮流程。

### 6. 以最终产物做隔离审计

暂时丢弃创建讨论、参考版本和预期答案，只读取最终 Skill 及其现行资源，重新确认：

- 新会话能否独立理解何时触发、如何执行、何时停止以及交付什么。
- 是否与已有 Skill 重复或争抢同一触发；排他边界能否阻止合理反例。
- 每个规则和资源是否实际改变行为；是否仍有占位符、过程残留、死引用和无价值复杂度。
- 验证结论是否严格受已执行证据支持，没有把静态通过写成行为有效。

发现问题就继续收敛最终 Skill，不用补充解释来维护有缺陷的结构。

## 完成要求

完成前确认：

1. 新 Skill 具有独立、可复用且不与现有能力重复的职责。
2. `name`、`description`、正文、资源、协作边界和路由一致。
3. 没有占位内容、无用目录、失效引用、来源不明资源或平台不兼容机制。
4. 已执行与风险匹配的静态、路由和必要行为验证，并如实保留未验证边界。
5. 只完成用户授权的创建及直接关联维护；安装、启用、外部写入和发布状态分别说明。

最终只交付实际创建内容、核心职责、验证结果和真实未完成项，不复述完整设计过程。
