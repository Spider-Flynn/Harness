# unit-test

## 定位

`unit-test` 只负责设计、编写和运行白盒单元测试。它读取已确认的目标行为、测试场景、当前
代码和业务项目约定，直接调用被测单元并隔离边界外依赖，不选择开发流程、不安排其他 Skill，
也不修改生产代码。

没有真实 HTTP 入口的功能可以把单测作为主要测试证据；具有 HTTP 入口的功能只能用单测补充
复杂内部逻辑的白盒证据，完整 API 行为仍须由真实 HTTP 证明。

单测只证明被测代码在给定输入和 Mock 交互下的返回、状态变化与协作行为。它不证明真实
Spring 装配、调度注册、数据库事务、Redis、MQ 投递与消费、外部系统连接或端到端副作用。

## 适用条件

在以下范围内使用本 Skill：

1. 定时任务、消费者、CLI、批处理、内部处理器、Service 或公共组件没有真实 HTTP 入口，
   且包含业务规则、分支组合、状态流转、幂等、重试、边界或异常处理。
2. 同一内部能力被多个入口复用，需要用白盒测试保护共享契约。
3. API 内部包含真实 HTTP 测试难以低成本穷举的算法、状态机、分支组合或下游参数转换，
   需要补充白盒证据。
4. 已有单测直接覆盖本轮受影响的内部契约，需要运行或补充相关回归。

简单字段赋值、一对一映射、薄 CRUD 或框架样板代码，不为覆盖率数字或测试形式单独新增单测。
服务未启动、鉴权缺失或外部环境不可用也不构成单测触发条件，不能用 Mock 结果替代本应完成的
真实 HTTP 验证。

## 执行模式

测试先行或最终验证由当前任务预先确定，本 Skill 不自行选择。

- **测试先行**：先编写能够执行且锁定目标行为的测试并运行。只有测试因目标行为缺失或错误
  而失败，才形成有效 Red；编译错误、测试框架错误、缺失 Mock 或错误数据不是业务 Red。
  记录失败断言和实际结果后停止，不在本 Skill 内编写生产代码。
- **最终验证**：依据已实现行为复用或补充测试，运行目标测试及直接相关回归，形成当前结果。
- **既有行为保护**：需要锁定未变更的旧行为时，测试应在修改前通过；已确认的新需求改变旧
  预期时，才同步更新对应断言并说明变化依据。

## 白盒测试设计

1. 阅读被测单元及其直接契约，识别会改变业务结果的输入、分支、状态、异常和边界。
2. 每个测试只表达一个可判断场景，断言返回值、异常、状态变化或关键协作参数中的实际业务
   结果，打印输出不能替代断言。
3. 对定时任务、消费者、CLI、批处理和内部处理器，直接调用可测试入口，验证业务处理与下游
   交互；不得把这种直接调用表述为真实调度、真实消息、真实命令环境或真实基础设施已通过。
4. 对 API 内部逻辑，只覆盖灰盒调用不易穷举且具有回归价值的复杂路径，不重复 HTTP 层的
   请求绑定、鉴权、响应序列化或完整副作用断言。
5. 输入或代码路径只有在会改变返回、异常、状态、下游参数或持久化意图时，才形成独立用例；
   不按代码行数或分支覆盖率机械凑场景。

当每个命中本 Skill 的高风险规则都有对应测试，关键异常与边界具有有效断言，且未覆盖项及其
证据边界已说明时，测试设计即可停止。

## Mock 与测试数据

1. Mock 数据库、Redis、MQ、HTTP 客户端、文件系统、时钟及其他被测边界外依赖；不要 Mock
   本轮要验证的业务逻辑。
2. Mock 返回值只包含当前路径所需数据；枚举、状态、类型、必填字段和边界值应来自当前代码、
   契约、配置、已有测试或明确需求。
3. 下游调用本身是业务结果时，使用参数捕获或等价机制断言调用次数和关键字段；仅配置 Mock
   返回值不能证明协作行为正确。
4. 外部依赖的 Mock 成功只证明调用意图符合预期，不证明真实连接、事务、投递或副作用成功。

## 测试文件

优先复用直接覆盖被测单元的已有测试文件，命名、目录、框架、分组、标签和断言风格服从业务
项目现状。没有现成约定时，Java/JUnit 测试使用 `*Test` 后缀，以业务场景命名测试方法，并
用 `@DisplayName` 或等价说明表达场景与预期；只有分组能提高可读性时才使用 `@Nested`。

新增或修改测试后，同步维护文件内直接相关的场景说明。不得通过删除断言、放宽断言、跳过
测试或 Mock 被测逻辑来制造通过。

## 失败与输出

测试失败时，先区分测试数据、Mock 边界、断言预期和生产行为。能够确认测试自身错误时，只
修正测试；生产行为与已确认预期不一致时，保留失败证据，不在本 Skill 内修改生产代码。

完成后说明：

1. 新增或修改的测试及其业务规则、代码路径和关键断言。
2. 实际运行的命令、通过与失败结果，以及有效 Red 或 Green 的判断依据。
3. 本次单测是无 HTTP 功能的主要证据，还是 API 内部逻辑的补充证据。
4. 未覆盖路径、真实依赖与装配边界，以及仍不能由单测证明的事项。
