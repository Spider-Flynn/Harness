# Debug

## 定位

`debug` 负责在不修改仓库内容的前提下定位问题，形成可复核的根因结论或明确的未知项。它
可以读取源码、配置、日志和运行状态，并执行安全、非破坏性的现有诊断或复现命令；不得修改
生产代码、测试代码、配置、断言或预期。

没有证据时不把猜测写成结论。只有根因已经验证且正确预期清楚时，才说明与根因对应的最小
修复边界；不在本 Skill 中实现修复、设计测试或安排后续执行。

## 输入与事实边界

优先收集：

1. 实际异常与正确预期之间的差异，以及正确预期的来源。
2. 完整错误日志、堆栈、失败命令、时间范围和关联标识。
3. 复现步骤、输入参数、环境、数据状态和发生频率。
4. 最近变更、相关配置、源码入口和已尝试的排查动作。

区分直接观察、外部提供的事实、从源码得到的推断和待验证假设。正确预期本身不明确时，先
说明无法判定是缺陷还是预期行为；关键日志、环境或数据不可得时，列出缺口及其对结论的影响。

## 诊断过程

1. 完整读取错误信息和上下文，建立现象、时间、输入、环境与预期的事实基线。
2. 优先复用已有证据；证据不足且现有入口允许安全复现时，使用最小输入确认触发条件。复现若
   会写入生产数据、触发外部副作用或改变仓库内容，必须停止并说明所需条件。
3. 从真实入口沿调用链、数据流或配置链逐层追踪输入与输出，确定第一次偏离预期的位置。
4. 检查最近变更和同项目内相似的正常路径，提取能够区分原因的差异，不把时间相关性直接当作
   因果关系。
5. 基于已有证据提出一个可证伪的根因假设，写明如果假设成立应观察到什么。
6. 一次只核查一个能够区分假设的变量，用最小只读动作验证并记录原始结果。任何需要改变
   数据、缓存、配置、进程或外部状态的验证都停止执行，只说明所需条件。假设被推翻后回到
   证据链，再提出下一个假设，不在失败尝试上叠加变化。
7. 复核根因能否同时解释触发条件、错误表现和影响范围；不能解释的现象保留为未知项。

## 假设验证规则

1. 假设必须明确关联已有证据，并能被观察结果证明或推翻。
2. 静态源码只能证明可能路径；运行日志、复现结果、数据状态和边界观测分别只证明其覆盖范围。
3. 相关性、异常附近的代码和最近提交都不是独立的根因证据。
4. 多次假设失败或证据互相冲突时，停止沿原路径猜测，重新检查正确预期、环境、数据和架构
   前提。

## 跨层证据链

当问题跨 Controller、Service、DAO、DB、Redis、MQ、外部接口或构建环境时，按边界收集证据：

1. 每层输入是什么。
2. 每层输出是什么。
3. 配置或上下文是否正确传递。
4. 哪一层开始出现错误。
5. 是否存在测试数据或环境状态问题。

只有能够指出第一个异常边界及其上游来源时，才把链路推断提升为根因；只定位到最终抛错位置
仍属于症状定位。

## 结论与修复边界

根因已验证后输出：

1. 根因、触发条件以及从现象到根因的关键证据链。
2. 已确认影响范围，以及仍无法由根因解释或尚未验证的事项。
3. 正确行为与错误行为的差异、根因对应的最小修改位置和必须保持不变的行为。
4. 修复可能涉及的兼容性、副作用和环境前提。

根因未验证时输出当前最强假设、支持与反对证据、未知项和继续确认所需的最小证据，不提供
具体补丁或把问题写成已定位。修复边界只是诊断产物，不得表述为已经修复或验证。

## 禁止事项

1. 不修改生产代码、测试代码、配置、断言或既有预期来验证猜测。
2. 不同时尝试多个假设，不在失败尝试上继续叠加变量。
3. 不把最终抛错位置、相关代码或环境差异直接当作根因。
4. 不把无法复现、证据不足或只经静态阅读的问题写成已确认根因。
5. 不选择、调用或安排编码与测试能力，不把修复边界写成已完成修改。
