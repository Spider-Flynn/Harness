# 测试设计

## 定位

`test-design` 只负责把已确认的目标行为和约束转换成需求级测试场景与可判断预期，回答“哪些业务差异需要验证，以及观察到什么结果才能判断行为正确”。

它是可独立使用的单点能力，不要求先形成技术设计文档，也不选择单测、HTTP 集测或其他测试实现方式，不编写或修改测试代码、生产代码。

## 输入与事实边界

开始设计前，确认现有材料足以判断：

1. 本次目标行为、范围和适用约束。
2. 每种业务差异下应当观察到的正确结果。
3. 涉及接口或既有能力时，适用的契约、当前行为和兼容责任。
4. 测试场景成立所需的数据、状态、权限、环境或外部依赖条件。

这些信息可以来自用户确认、需求材料、接口或行为契约、已有测试、当前实现以及技术设计。技术设计只是可选事实来源，不能替代目标行为和预期结果本身。

先读取能够直接回答当前测试问题的材料，再区分已确认目标、证据支持的当前行为、合理推测和未决事项。当前代码和旧测试只证明现状，不自动代表本次正确预期；材料不足以判断结果时，说明受影响场景并集中确认，不在本 Skill 中猜测需求或改写目标。

## 测试场景设计规则

1. 按目标行为、规则、接口或状态变化划分行为单位，建立场景与依据之间的可追溯关系。
2. 只为会导致业务结果不同的条件设计独立场景。正常、边界、异常、权限、状态、兼容和副作用是检查维度，不是必须机械补齐的数量清单。
3. 明确受影响的既有行为，并只在本次影响范围内设计回归场景，不扩张为全系统补测。
4. 既有行为缺少清楚预期时，先记录保护旧行为所需的场景和未决预期；只有已确认目标明确改变旧行为时，才把新预期作为当前有效依据。
5. 每个预期都必须能够从外部观察并作出判断。动态时间、随机 ID、异步结果或最终一致状态无法写死时，写明判断规则、允许范围、等待条件或最终状态，不伪造固定值。
6. 测试数据、状态、权限、请求上下文、环境和外部依赖只写使场景成立或影响结果判断的条件。
7. 涉及数据、状态或外部动作时，分别说明预期响应、持久化结果、状态变化和关键副作用；不存在的维度不保留空项。
8. 需求级场景描述业务输入、操作和可观察结果，不展开代码分支、测试类、Mock 写法或测试实现类型。

## 用例内容

每条用例按实际需要包含：

1. 用例 ID、场景名称、性质及其对应的目标行为、规则或契约。
2. 前置状态、必要数据、权限、环境和外部依赖。
3. 输入或操作。
4. 可观察且可判断的预期响应、异常、数据、状态和关键副作用。
5. 必要的清理、回滚、等待或重复执行要求。

同一条件同时影响多个结果时，在一条场景中完整描述；条件和预期不同才拆分。不同场景共享的背景可以在范围说明中统一定义，不在每条用例中重复大段事实。

## 未决事项

能够继续设计的部分先完成。对于确实无法判断的条件或预期，记录所属行为、现有证据、建议及依据、不同选择的影响和需要补齐的决定；合并相同根因的问题，避免按用例重复询问。

建议只能标为建议，不能写成已确认预期。获得新事实后，同步更新所有受影响场景并删除已解决事项；未解决事项继续保留，并明确因此尚未覆盖或无法判断的范围。

## 模板与产出

需要稳定保存测试规格、目标项目没有更权威模板，且统一结构确实能降低遗漏风险时，读取 `assets/test-case-template.md`。只需在当前任务中确认少量场景时，直接交付场景和预期，不为使用模板而创建文件。

产出位置、文件名和是否形成独立文档服从当前任务与目标项目规则。文档只保留当前有效的范围、依据、场景、预期和未决事项，不记录讨论过程、临时草稿或被替代预期。

目标行为或契约变化时，依据新的已确认事实同步更新所有受影响场景；未确认的新解释不能覆盖现行测试基线。

## 完成自检

完成前确认：

1. 已确认的目标行为和受影响既有行为都有对应场景，且没有为了数量生成无业务差异的用例。
2. 每条场景都能追溯到目标、规则、契约或已确认的既有行为。
3. 前置条件、输入或操作以及预期结果清楚、可执行、可观察、可判断。
4. 回归范围与本次影响一致，没有遗漏关键状态、权限、边界或副作用差异，也没有扩张为全系统补测。
5. 当前事实、目标预期、建议和未决事项没有混写，代码分支或旧测试没有被误当成需求依据。
6. 文档没有固定路径假设、测试实现细节、重复场景或空占位内容。
