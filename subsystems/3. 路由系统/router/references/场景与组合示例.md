# 场景与组合示例

先按事实条件找相近示例，再按当前任务的差异增减能力。以下示例用于降低重复判断成本，不是场景全集、
固定套餐或规模分级。没有相近示例时按 SKILL.md 的选择条件与依赖组合；不要为覆盖所有排列增加示例。

链路中的名称是具体 Skill，“修改”是直接动作；所有例子均以对应能力已接入可用、用户和项目没有其他
明确要求为前提。文档选择独立于能力选择；下面“无”只表示不新增独立任务文档，不表示删除已有资产。

| 当前事实 | 可复用链路 | 文档与调整边界 |
|---|---|---|
| 局部提示文案或常量替换，含义与影响明确，不改变规则、共享契约或其他功能 | `coding → 修改` | 无；不设计、不测试、不校验、不审计。若常量实际参与公共计算或协议，不能套用此例。 |
| 已有适用设计的薄 API 改动，内部映射简单，任务要求验证接口结果及相关回归 | `coding → 修改 → it-test` | 默认无；不为简单映射补单测、测试设计、TDD 或审计。 |
| 已证实的局部逻辑 Bug，有可运行的单元测试可稳定复现，修复边界清楚且不影响其他调用方 | `unit-test（Red）→ coding → 修改 → unit-test（Green／回归）` | 默认无；不重复 Debug，不强制独立设计、测试设计或审计。 |
| 多入口共享计算规则变更，技术方案已明确，但规则组合与不变行为需要整理，内部测试可以稳定表达预期 | `test-design → unit-test（旧行为基线与目标 Red）→ coding → 修改 → unit-test（Green／回归）→ audit（实现）` | 场景需后续复用时输出测试设计；无需 spec。若任务还需验证受影响 HTTP 入口，在审计前增加 `it-test`。 |
| 新增 API 的方案与验收场景均已确认，内部逻辑复杂，既需要单元 TDD 也需要真实入口验证，已确定需要实现审计 | `unit-test（Red）→ coding → 修改 → unit-test（Green／回归）→ it-test → audit（实现）` | 复用已有设计与场景，不重复调用 `tec-design`、`test-design` 或创建副本。 |
| 跨模块接口改造存在高返工成本的契约取舍，需要先审计方案；接口场景需整理，但实现规则简单，无测试先行要求 | `tec-design → audit（设计）→ test-design → coding → 修改 → it-test → audit（实现）` | spec 与测试设计需供后续实现、审计使用时落盘；不因跨模块就机械补单测或 TDD。 |
| 异常根因未知，目前无法判断修复对象及影响 | `debug`，返回诊断后才能确定的路线缺口 | 默认无；需要可回查诊断材料时才保存。HARNESS 获得结论后再请求路线，不提前承诺实现或测试组合。 |
| 只要求形成技术方案，并明确需要 spec | `tec-design` | 输出 spec；不自动实现、测试或审计。若明确要求独立审查方案，可增加 `audit（设计）`。 |
| 只要求梳理受影响功能的测试场景 | `test-design` | 按是否需要稳定复用决定测试设计文档；不自动技术设计、写测试代码或修改生产代码。 |
| 已有清楚用例，只要求补齐并运行内部单测 | `unit-test（最终验证）` | 默认无；不自动追加 `test-design`、生产代码修改或审计。发现生产缺陷时返回事实，不越过当前范围修复。 |

## 使用时的差异判断

- 相同“新增功能”标签可能使用短链、TDD、设计驱动或多能力组合；示例中的条件才是复用依据。
- 用例已经清楚时，测试 Skill 可以直接使用，不为了 TDD 固定增加 `test-design`。
- 只有少量设计结论也可调用 `tec-design` 而不生成 spec；加载设计能力与落盘不是同一选择。
- 未知影响只补充足以改变路线的事实；既不当作低影响，也不把所有保障环节全部打开。
- 所需测试能力缺失或环境不可用时，说明缺口；不能套用“不测试”的简单任务示例来消除缺口。
- 采用 TDD 或其他流程简称时仍写出具体 Skill 与模式；只保留对当前任务有用的节点和必要产物。
