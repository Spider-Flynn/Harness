# Router

根据当前任务选择具体 Skills、执行顺序和模式，说明需要与跳过的环节，以及是否生成独立文档。
路线交给 HARNESS 执行；Router 不调用能力，不展开编码方法、文档正文、测试实现或审计方法。

## 形成路线

1. 使用已确认目标、范围、约束、必要项目事实和当前可用能力。用户只要求设计、测试或诊断时，只
   规划该范围，不自动追加实现；用户和项目的明确要求优先于场景中的默认选择。
2. 从 [场景与组合示例](references/场景与组合示例.md) 复用相近条件，只核对会改变路线的差异，再按
   下述选择条件增减环节。没有相近示例时直接组合能力，不为套用示例扩大或缩小任务。
3. 只选择 HARNESS 提供的当前已接入且可用的业务能力。下表和示例描述能力用法，不证明能力已接入；
   不虚构 Skill，也不因某能力已安装就调用。缺少必要能力时返回具体缺口和仍可执行部分。
4. 按事实依赖安排已选能力的先后，同一 Skill 可以在不同位置以不同模式再次使用。场景不是封闭的
   路线全集，TDD、SDD 等名称也不能替代实际 Skill 链路。

只有事实缺口会改变能力选择、顺序或产物要求时，才返回缺口交由 HARNESS 补齐；不要求完整项目画像。
能力内部需要的局部事实留给对应 Skill，不为规划路线提前完成设计、测试设计或全仓调查。

## 实现复杂度与存量影响

分别判断实现是否复杂、是否影响存量，不用文件数量、代码行数或“新功能／Bug”标签决定路线。

- **简单改动**：目标和实现选择明确，可沿用现有模式，规则之间没有明显耦合，修改及影响边界清楚。
- **复杂改动**：存在会改变结果的方案取舍或模块职责调整，或者多条规则、状态、数据关系、依赖相互
  影响，不能逐项独立处理。复杂实现不必然影响已有功能，局部少量代码也可能改变共享行为。
- **存量影响**：区分修改已有代码与改变已有行为。确认改动是否必要、是否有影响更小的做法，以及
  哪些已有功能、调用方、接口或数据含义会改变，哪些必须保持不变。仅涉及旧文件不自动升级整条路线。

影响尚不清楚时返回会改变路线的具体缺口，不假定没有影响，也不据此展开全系统检查。所有环节围绕
本次需求及实际受影响范围选择，不为无关存量问题、理论风险或顺手重构增加流程。

## 能力选择条件

简单、局部且影响明确的改动，用户和项目没有额外要求时，直接修改；不执行设计、测试、校验、审计，
不生成独立文档。只报告实际修改，不把跳过验证描述为验证通过。

其他任务按下列条件组合，不因选中一个能力而默认开启其他环节：

| 能力或动作 | 选择条件 |
|---|---|
| `debug` | 异常原因尚未证实，需要先诊断；根因和修复边界已有证据时跳过。 |
| `tec-design` | 用户要求技术设计，或方案、模块职责、接口／数据契约、兼容与实现边界需要先明确；已有适用设计或方案直接明确时跳过。 |
| `test-design` | 用户要求测试设计，或多种业务差异、规则组合、受影响旧行为的测试预期需要先整理；已有适用场景或少量明确预期时跳过。它不依赖独立技术设计。 |
| `coding` 与修改 | 需要新增或修改生产代码时加载 `coding` 并执行修改；不把基础编码包装为额外 Skill。 |
| `unit-test` | 已决定需要测试，且要验证复杂内部规则、共享逻辑或已有单元测试覆盖的受影响行为。 |
| `it-test` | 已决定需要测试，且要验证当前改动涉及的真实 HTTP 行为、接口契约或相关回归。内部规则也需要单独覆盖时可与 `unit-test` 组合。 |
| `audit` | 用户要求独立审计，或复杂变更、共享行为、公共契约与架构影响需要独立核验。简单局部改动默认跳过；不因为修改旧文件就自动加入。 |

是否执行测试先于测试类型选择；不运行测试也是合法选择。需要其他真实入口证据时，仅使用当前可用
且适用的能力；能力或环境缺失是验证缺口，不是改判为“无需测试”的理由，也不能用单测、Mock 或静态
检查冒充真实入口通过。编译、构建或静态检查若为当前任务所需，作为具体动作说明，不虚构校验 Skill。

## 必要顺序与执行模式

- **诊断与设计**：只有后续选择依赖它们时才前置。根因未知且无法确定修复链路时，先返回 `debug`
  及待确认事项；HARNESS 获得结论后再请求修复路线，不预设诊断一定导致代码修改或完整开发链。
- **测试后置**：实现方式明确、需要结果验证但不需要失败测试约束实现时，在修改后执行选定测试。
- **TDD**：可稳定复现的 Bug、复杂业务规则或重要共享行为变更，能够获得有效失败反馈时优先测试
  先行。明确采用哪个测试 Skill：目标行为的有效 Red → 修改 → 同一目标的 Green 及相关回归。
  编译失败、服务未启动、数据缺失不算业务 Red；无法形成有效 Red 时保留事实缺口或选择测试后置，
  不伪造已完成 TDD。是否需要独立 `test-design` 和测试文档另行判断。
- **存量行为保护**：需要锁定不变行为时，安排相关测试在修改前通过、修改后继续通过；这不是制造 Red。
- **审计位置**：实现审计放在实现结果及所选验证完成后；方案取舍、契约或高返工成本需要提前核验时，
  可在实现前审计设计。两者可以独立选择或组合，不能用设计审计代替实现审计。

`intent`、项目知识读取与沉淀的进入仍由 HARNESS 决定；`rules-know` 是知识能力的只读依赖，个人与
演进能力不加入开发路线。HARNESS 交回确需独立审计的知识候选时，只补充 `audit` 的对象和位置，
不把每次知识沉淀都变成必经审计。

## 独立文档

分别决定是否需要 spec、测试设计文档、测试结果或审计报告，不因加载 Skill 就自动生成文件。
用户要求文档，或关键结论需要跨会话、独立审计、协作与后续维护且会话不足以承载时，选择独立产物；
已有适用产物直接复用，只需短结论时留在会话中。需要设计不等于必须输出 spec，TDD 也不等于必须
输出测试设计文档。

Router 只说明产物类型与用途；HARNESS 按 Runtime 统一任务目录和命名，对应 Skill 负责具体内容、
结构与质量。无需另建路线文件、交接协议或通用任务对象。

## 路线输出

用短链路或简短文字说明：

1. 本次选择的具体 Skill、直接动作、执行顺序及必要模式，如 `unit-test（Red）`、`audit（设计）`；
2. 与本次有关的跳过项，明确是否不测试、不校验或不审计，不穷举所有未选能力；
3. 是否输出哪些独立文档；需要写文件时使用 HARNESS 提供的统一任务目录；
4. 改变选择的关键依据和仍需补齐的事实或能力，不重复完整判断过程。

同一任务可以只有一个 Skill，也可以组合多个、在不同阶段再次使用同一 Skill。不以模式名、固定套餐
或抽象的“设计—开发—测试”代替本次实际选择。

## 重新规划

目标、范围或验收变化，新事实推翻路线依据，能力不可用或路线不可执行，实际影响扩大，或反馈要求
改变环节时，由 HARNESS 重新调用 Router。普通节点完成后继续原路线，不为每一步重复规划。
