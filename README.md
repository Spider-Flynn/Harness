# Harness Engineering

Harness Engineering 是围绕 Agent 和 LLM 的运行与编排框架。本仓库当前实现软件工程领域实例，
通过可组合能力、运行时约束和真实证据，支持软件任务的理解、执行、验证、审计、知识沉淀与受控演进。

当前仓库已确认框架、领域实例与具体实现的分层边界；软件工程实例的五个业务任务职责域和 Harness
框架演进控制面已有初步实现，但 Harness 尚未启用，也未经过真实业务项目的完整任务验证。

## 项目结构

| 路径 | 职责 |
|---|---|
| `AGENTS.md` | 本仓库自身的边界、维护规则和长期协作约束 |
| `cmd/` | AI 接入提示词，一条命令一个文件，按需加载 |
| `TODO.md` | 当前整体重构、二次实现、验证和未决问题 |
| `docs/` | 已确认的系统设计，以及明确标注的讨论候选 |
| `runtime/HARNESS.md` | 接入业务代码仓库后需要加载的唯一运行合同 |
| `systems/` | 可插拔领域系统清单，声明 Runtime、Skill 和资源投影 |
| `subsystems/` | 按职责域组织的子系统实现，包括 Skills 及共享规范、模板等资源 |
| `scripts/` | 统一 CLI 入口及分模块的业务项目接入实现 |
| `data/` | 本地绑定项目索引等轻量数据，按需生成，Git 忽略 |

主要入口：

- [系统设计](./docs/系统设计.md)：整体定位、边界、职责域和设计原则。
- [外部实践与设计候选](./docs/外部实践与设计候选.md)：资料提炼与讨论输入，不是已确认设计或实施计划。
- [运行合同](./runtime/HARNESS.md)：业务项目运行时的公共编排语义。
- [TODO](./TODO.md)：当前实施顺序、依赖和验收门禁。

## 当前软件工程领域实例

以下五个职责域属于当前软件工程领域实例，不是 Harness 框架要求。其他领域实例可以定义不同的
子系统、过程产物、结果产物和运行路线；演进属于 Harness 框架控制面，不是软件工程业务任务职责域。

| 层面 | 职责或能力 | 当前公开能力 |
|---|---|---|
| 软件工程实例 | 意图接入 | `intent` |
| 软件工程实例 | 知识 | `know`、`build`、`rules-know`（只读规则依赖） |
| 软件工程实例 | 路由 | `router` |
| 软件工程实例 | 执行 | `tec-design`、`test-design`、`coding`、`debug`、`unit-test`、`it-test` |
| 软件工程实例 | 审计 | `audit` |
| Harness 框架控制面 | 演进 | `retro`、`skill-creator`、`skill-neat` |
| 横向能力 | 上下文隔离与独立验证 | `subagent` |
| 额外能力 | 按个人或场景触发 | `biz`、`cr` |

`cooper` 与 `mock` 是永久仅限本机的能力目录，由根目录 `.gitignore` 排除，不属于公开仓库源码；
是否在本机业务项目中投影，另按接入条件和授权决定。

五个业务任务职责域不是固定五段流水线。HARNESS 根据当前意图、上下文和反馈决定是否进入意图、知识或
路线规划；`router` 参考相近场景，按目标、实现复杂度与存量影响组合具体 Skills、顺序、产物、测试和审计，
宿主主会话负责按路线加载能力并执行。Skill 是能力与规则单元，不是独立角色，也不自行选择下一能力。

知识沉淀由知识系统独立完成：HARNESS 在任务形成稳定结果后按需调用 `know`，由它从过程产物和
可回查事实中提取长期有效内容，并按业务画像、运行模型、功能和数据源单独维护。
`build` 是可选的首次或结构性知识建设能力，没有知识库不阻断正常需求。人工 Review、风险接受、发布
和回退由用户自行决定；Agent 只有获得明确授权后才能执行对应的外部写操作。不再设置交付职责域，
`cr` 仅供用户审阅后主动反馈时使用，不进入 HARNESS 编排或默认项目投影。

生产代码由宿主主会话实现并加载 `coding`。它承载个性化编码习惯和本机环境使用约束，不教授 Agent
基础编码能力，也不是测试、自检或路线规划能力。

开发路线不是几个固定套餐：设计、测试设计、TDD、测试类型和审计按需组合，也可以只完成设计或诊断。
用户和项目没有额外要求时，简单局部改动可以直接修改，不执行测试、校验或审计，不生成独立文档。
未执行的检查不会被描述为通过；所需能力不可用时会明确说明缺口。

路线需要独立审计时，主会话按 `audit` 创建只读、干净上下文的 Audit Subagent；它只返回结论、问题、
证据和建议，修改仍由主会话完成。同一审计最多三轮，初审计为第一轮；第三轮后仍存在的实质分歧或
证据缺口会如实交给用户。Subagent 只用于临时分支、并行或独立判断；只有用户明确需要长期单独跟进
时才创建新的用户会话。

## 项目知识与任务文档

目标项目的知识保存在 `.harness/know/`，从其中的 `README.md` 导航；所有需保留的任务过程产物，
包括设计、测试、审计文档以及日志、截图，统一放在 `.harness/tasks/YYYYMMDD-任务简名/`，同一任务
后续修补沿用原目录。简单任务不必建文件，代码和测试代码仍放在项目原位置。具体命名见
[运行合同的信息与产物规则](./runtime/HARNESS.md#五信息与产物)。

需要建设知识时可主动调用 `build`：先提供业务材料、已有文档或其他信息源，再通过问答补齐。新项目
和存量项目都不默认扫描代码，确实缺少其他来源时才征得同意后局部读取。可以只建设当前需要的知识。
不运行 Build 也能正常开发；有长期价值的任务结果可由 `know` 建立最小知识入口或维护现有内容。

建设与维护共用知识系统内的 [rules-know](<./subsystems/2. 知识系统/rules-know/SKILL.md>)。它随 Skills
接入，由 Build 与 Know 沉淀按需读取，不需要用户单独调用，也不增加流程步骤；普通知识检索不加载它。
功能按业务模块组织；数据源用一个 `index.json` 描述核心源及实际依赖的外部表，SQL 和数据集保留
原生文件格式。文档模板只是可裁剪骨架，不要求填满固定表格。

## 接入工具

第一版接入采用“确定性 CLI 核心 + AI 辅助交互”。AI 可以帮助用户判断项目和组织参数，但所有绑定
操作都通过 `scripts/harness.py` 执行。内部已按命令和职责拆分，使用时不需要逐个运行 Python 模块。

接入工具使用 Python 3.10+ 和标准库，依赖 POSIX 文件锁与符号链接，适用于 macOS/Linux；当前冒烟
验证环境为 macOS，未适配原生 Windows。不需要额外安装 Python 依赖。

在已读取本仓库 `AGENTS.md` 的 AI 会话中，可以直接说 `init`，或说“init，把软件工程系统接入
`/你的项目目录`”。AI 会按 [init 指引](./cmd/init.md) 收集必要选择、执行脚本并反馈检查结果；已有绑定
可说 `relink`，也支持 `doctor`、`remove`、`list` 及对应的自然语言请求。这些是本仓库的对话约定，
不是全局命令。该对话入口仍是未正式启用的初稿，尚未经过真实接入会话验证。
`cmd/` 中的指引负责 AI 交互，实际操作调用同一 CLI，与手动执行使用相同实现。

也可以自行运行以下 CLI 命令：

```bash
python3 scripts/harness.py --help
python3 scripts/harness.py init --project <业务项目目录>
python3 scripts/harness.py doctor --project <业务项目目录>
python3 scripts/harness.py relink --project <业务项目目录>
python3 scripts/harness.py remove --project <业务项目目录>
python3 scripts/harness.py list
```

当前只有 `software-engineering` 领域系统，因此 `init` 会自动选择；未来增加系统后可通过 `--system`
选择。`init` 默认要求目标目录存在 `.git`，AI 或用户已经确认非 Git 目录仍适用时，可显式增加
`--allow-non-git`。领域 Manifest 将能力分为默认、条件、本机、横向、个人和演进六类：默认与横向
能力自动投影，条件与本机能力通过可重复的 `--with-skill <name>` 选择，个人和演进能力不进入业务项目。

绑定后，目标项目中的 `.harness/runtime/HARNESS.md` 和 `.agents/skills/<skill>` 都是指向本仓库
唯一源码的软链接，知识规则统一位于 `.agents/skills/rules-know/`；`.harness/manifest.json`
保存该项目选择的系统、规则入口、可选能力、链接及受管 Git Hook，本仓库
`data/projects.json` 只作为 `list` 的项目索引。所有本地辅助数据保存在本仓库 `data/` 下并由 Git
忽略，不写入用户主目录。接入工具在现有 `AGENTS.md`、`CLAUDE.md` 中维护最小加载片段；两者都不
存在时，交互模式会说明生态并询问创建哪一个，非交互模式必须通过 `--rules` 明确指定。

软件工程系统接入普通 Git 工作树时，会安装 `.git/hooks/pre-commit` 和
`.git/hooks/prepare-commit-msg`，阻止在 `main`、`master`、`test`、`pre` 直接提交。前者尽早拦截，
后者不受 `git commit --no-verify` 抑制。拦截不会丢失当前修改，用户切换或创建开发分支后可继续；
工具不会自动切换分支。项目已有同名 Hook 时分别保存在同目录的 `<hook>.harness-original`，并在允许
提交的分支继续执行；解绑时校验摘要或链接目标并恢复原文件。为避免影响其他仓库或共享配置，当前
拒绝符号链接 `.git`，也不自动接管 linked worktree 或设置了 `core.hooksPath` 的项目；显式接入非 Git
目录时不安装提交门禁。门禁通过不代表 Agent 已获得 Commit 或 Push 授权。

`relink` 复用目标项目清单中的原选择，重新建立 Runtime、Skills、规则片段、Git Hook 和本机索引，不重新选择
项目或领域系统；Harness 源目录移动或链接损坏后也使用该命令修复。`doctor` 只检查，`remove` 只移除
受管链接、片段、Git Hook 和记录，并恢复接入前的两个 Hook，保留 `.harness/know/`、
`.harness/tasks/` 及其他项目内容。旧绑定运行 `relink` 可补齐 `rules-know`、Git Hook，并清理清单中
原有的知识资源链接；已有知识也不妨碍重新 `init`。当前未提供会话前 Runtime Hook 加载器和 TUI。

本机索引是辅助缓存：缺失或损坏不会阻断目标项目的 `doctor`、`relink` 或 `remove`。`relink` 会将
内容损坏的普通索引隔离备份并重建当前项目记录；若索引路径被目录或软链接占用，工具会要求用户先
移走该精确冲突项再运行 `relink`。`list` 无法读取索引时会返回对应的可执行恢复提示。

上述接入链已通过临时 Git 目录的受控冒烟，但尚未接入真实业务项目，也不代表软件工程 Harness 的
需求开发、知识沉淀、审计和演进主链已经验证或启用。`build` 始终是可选能力。
