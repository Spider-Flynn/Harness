# Harness 运行合同

> 当前状态：整体结构重构中的初步合同，未启用，尚未经过真实业务任务验证。

本文件是接入业务项目后需要加载的唯一 Harness 运行时合同。它只维护跨能力的公共运行语义，
不复制仓库维护规则、Skill 内部方法、接入脚本实现或 Harness 演进过程。

## 一、加载与边界

1. 先读取业务项目自身适用的用户级和项目级规则。业务项目规则、代码、项目知识和外部系统事实
   仍由业务项目维护；发生冲突时暂停并交给人裁决。
2. 再加载本文件，由 HARNESS 建立当前任务的全局编排视角。
3. 只加载当前任务需要的能力、来源、产物和证据。能力按需组合，不默认经过固定职责域主链。
4. 当前接入工具通过业务项目规则文件（如 `AGENTS.md`、`CLAUDE.md`）中的受管入口引导加载本文件；
   未来宿主 Hook 可以提供等价加载适配，但不得复制或替换本文件的唯一运行合同地位。

## 二、编排职责

HARNESS 是跨系统调度的唯一所有者。它决定是否进入意图或知识能力、何时调用 `router`、如何让
宿主主会话按路线加载和执行能力、何时重新规划，以及如何处理反馈、知识沉淀和最终结果。

`router` 是软件任务执行路线规划者。它优先参考相近场景，再按当前目标、实现复杂度与存量影响组合
具体 Skills、直接动作、顺序和模式，并决定独立文档、测试与审计要求。场景不是封闭的路线清单，能力
可以省略、组合或在不同阶段再次使用；没有适用场景时按选择条件组合。它返回路线但不直接执行。

宿主主会话是默认执行主体，Skill 是主会话按需加载的能力与规则单元，不代表独立角色。Skill 只负责
被加载后具体怎么完成以及自身产出内容，不判断自己是否应该运行，不选择下一个能力，也不管理跨系统
回流。生产代码由主会话修改并加载 `coding`；`coding` 只提供个性化编码习惯和本机环境使用约束，
不负责路线、测试、自检或审计。

### 全程适用的操作约束

- 人工 Review、风险接受、发布和回退由用户自行决定，HARNESS 只管理 Agent 的计算机侧工作。
  用户自行完成的操作不要求回填状态。
- Agent 执行 Commit、Push、PR、提测、部署、发布或其他外部写入前，必须有覆盖当前动作、目标和范围
  的明确用户授权。用户当前消息已经明确要求具体操作时即构成授权，不重复询问；授权不自动延伸到
  未提及的目标、后续重试、回退、扩大范围或其他外部动作。一条明确请求可以同时授权其中逐项列明的
  多个动作。
- 执行前重新核对实际目标、当前状态和适用门禁；能够使用宿主审批、权限或专用受控工具时优先使用。
  Git Hook 只证明分支策略满足，不证明用户已经授权。命令包装器只有在宿主能阻止绕过包装器直接调用
  底层工具时才构成确定性门禁；具体宿主适配仍待实现与验证。
- Agent 只报告实际执行并观察到的工具结果和外部状态。任一步失败或只完成部分动作时立即停止后续
  依赖动作，说明已经发生的状态、失败点和未完成项；没有新的明确授权，不自动重试、回退或改走影响
  更大的替代操作。
- 当前软件工程实例通过目标 Git 项目的受管 `pre-commit` 与 `prepare-commit-msg` 阻止在 `main`、
  `master`、`test`、`pre` 直接提交，后者不受 `--no-verify` 抑制。命中门禁时停止并提示用户创建或
  切换开发分支，保留当前未提交修改；Agent 不自动改变分支策略。门禁通过只说明当前分支允许提交，
  不代表已获得提交授权。

## 三、运行循环

用户明确请求首次或结构性知识建设时，直接加载 `build`，不先规划一条开发路线。Build 完成必要问答、
形成候选并按当前授权写入；如确有额外审计需要，由 HARNESS 交给 Router 安排，不由 Build 自行调度。
其他软件任务使用以下循环：

1. 读取用户输入和业务项目规则。只有不同理解会实质改变行动时，才调用 `intent` 对齐目标、范围、
   验收、约束和授权缺口；明确请求直接作为路线输入。
2. 使用当前需求、已知事实和可用能力调用 `router`。能力范围以目标项目绑定清单和当前可用 Skill
   入口为准，提供名称与职责即可；已知信息直接复用，不为规划提前加载全部 Skills。如果信息不足以
   形成路线，Router 只返回会改变路线的事实
   缺口。项目存在知识入口且缺口属于共享项目知识时，HARNESS 才调用 `know` 核验后重新规划；项目
   没有知识库时直接跳过任务前 `know`，主会话与执行 Skill 按需读取局部代码、项目规则和用户材料。
   默认只检查 `.harness/know/README.md` 是否存在，不为判断可用性加载 Know、遍历知识目录或维护
   绑定时的可用性快照。入口不存在表示暂无知识入口；存在但无法读取时如实返回问题，不伪装成无知识。
3. Router 输出当前任务的具体链路，HARNESS 按顺序执行所选 Skills 和直接动作。执行前确认所选 Skill
   入口可读；缺失时返回能力缺口，不虚构能力或自动修改绑定。只提供当前工作必需的事实、规则和产物
   引用，不额外插入未选择的设计、测试、校验或审计。
4. Skill 返回实际结论或修改、正式产物位置、已获得的证据与边界，以及仍缺失或无法继续的事项。
   HARNESS 判断继续当前路线、向用户询问、补充事实或重新规划。
5. 按所选路线完成代码修改、测试验证及独立审计后，由 HARNESS 判断过程产物、实际结果和可回查事实
   是否包含需要长期维护的项目知识变化。需要时调用 `know` 的项目知识沉淀能力，由它按项目既有知识结构提取；
   项目没有知识库时允许建立本次结果所需的最小知识入口。过程产物只作为知识来源，不替代独立维护
   的知识内容。
6. 因为知识沉淀基于已通过测试和审计确认的事实基线进行提取，`know` 写入后执行写后回读自检，
   默认无需额外 Audit Subagent 门禁；仅在发生核心模型颠覆性重构且用户明确要求时才按需补充审计。
7. HARNESS 汇总面向需求的实际计算机侧结果、知识沉淀结果、验证边界、审计结论和剩余问题，随后
   停止当前响应；不额外维护“任务已结束”状态。用户后续输入自然决定继续、修改、Debug 或开始新任务。
   若任务执行过程中出现多次返工或 Audit 达到上限等显著系统摩擦，HARNESS 在最终回复中可建议用户
   是否启动 `retro` 复盘。文件存在、模型自述、静态检查和 Mock 不能替代对应的真实行为。

用户审阅后可以主动调用个人反馈能力 `cr`，HARNESS 不调度它。用户要求继续工作时，主会话依据当前
请求和事实继续处理；反馈推翻路线依据时按下一节的条件重新规划。

## 四、执行路线

Router 根据任务独立选择以下内容，再按必要依赖组合；只请求设计、测试或诊断时不自动追加开发：

- 是否先进行技术设计，以及设计结论是否形成独立稳定文档；
- 是否需要测试设计，以及测试结论是否形成独立稳定文档；
- 是否采用 TDD，在修改实现前先获得有效失败反馈；
- 是否先定位根因，何时进入生产代码修改；
- 是否执行测试，以及使用 `unit-test`、`it-test`、两者或其他当前可用的测试能力；
- 是否需要独立审计、审计什么对象，以及审计位于哪一个风险边界；
- 具体 Skills 与直接动作的执行顺序、模式、相关跳过项和条件环节，不只返回 TDD、SDD 等模式名。

实现复杂度和存量影响分别判断，具体判据与场景由 Router 维护。用户和项目没有额外要求时，简单、局部
且影响明确的修改可以不执行设计、测试、校验或审计，也不生成独立文档；未执行就如实说明，不宣称
已经验证。原本需要的验证因能力或环境缺失而无法执行时，保留缺口，不能改称“无需验证”。

设计结论、有效 Red 等返回后继续路线中的修改和后续环节。已选测试发现局部实现错误，且目标、影响面
和环节未变时，在当前路线内修正并重跑相关测试，不为每次修正重新规划。

以下情况才重新调用 Router：用户目标、范围或验收变化；新事实推翻路线依据；当前能力证明路线不可
执行；实际影响面明显扩大；测试、审计或用户反馈要求增加、删除或重做环节。普通节点成功后直接
进入下一项，不为每一步重复规划。

## 五、信息与产物

Harness 不要求通用 Task、Action、版本或结束状态对象，也不要求每个任务建立文件。简单任务可以只
使用当前对话和业务项目已有资产；跨能力、跨会话或独立审计确有需要时，才保留必要的当前进展、产物
引用和证据。

Router 决定是否需要独立设计文档、测试文档等稳定产物，HARNESS 统一任务目录与命名，对应 Skill
决定产物的具体内容、结构和方法。框架统一将 Harness 管理的知识和需持久化的任务产物放在目标项目
`.harness/` 下，不能写回 Harness 源码仓库。当前软件工程实例使用以下分区：

- `.harness/know/`：独立维护的项目知识，`README.md` 是唯一总入口；
- `.harness/tasks/YYYYMMDD-任务简名/`：本次任务需保留的全部过程产物，包括设计、测试与审计文档、
  诊断材料、日志、截图、极简运行事件轨迹 `events.jsonl` 以及可选的 `retro.md`，按需创建，不机械生成空目录。
  `events.jsonl` 每行一条结构化事件，只记录关键状态迁移与摩擦点，包含：
  - `ts`：ISO 8601 时间戳；
  - `type`：事件类型，如 `route_selected`（路线规划与复杂度/存量判断）、`action_failed`（执行失败与重跑次数）、`audit_round`（审计轮次与结论）、`user_friction`（人工介入或分歧挂起）；
  - `data`：对应事实键值对，不记录大段代码或隐藏思维过程。
- `.harness/runtime/` 和 `.harness/manifest.json`：接入工具维护的运行入口及绑定记录，不用于存放
  项目知识正文；规则 Skill 与其他能力一起投影到 `.agents/skills/`。

首次需要写任务文件时，HARNESS 使用当日日期和简短任务名称确定一个目录，所有能力共用；任务简名
不包含路径分隔符，不同任务重名时追加短序号。同一任务后续修补、复审或跨日继续沿用原目录，不按
Skill、会话或执行轮次另起目录；既有任务目录直接沿用，不因命名规则变化自动搬迁。

默认按用途命名：`spec.md`、`测试设计.md`、`测试结果.md`、`审计报告.md`；仅创建路线需要的文件。
其他产物使用简短用途名并保留实际格式；同类不同对象需要分开保存时加对象前缀，如 `设计审计报告.md`。
后续能力直接引用已有位置，不复制平行文档，也不要求额外交接文件或目录索引。

代码、测试代码和正式迁移文件仍在业务项目既有位置；项目已有明确正式文档或知识位置时先确认沿用
还是迁移，不自动复制或搬移。HARNESS 只管理当前路线的引用和交接，不复制平行资产；Skill 按上述
位置组织具体内容。解绑只移除受管绑定，不删除 `know/`、`tasks/`；这两类内容不是安装缓存，不能
因 `.harness` 包含绑定文件就自动忽略或清空整个目录。

## 六、审计边界

Router 决定是否审计、审计对象和位置。需要审计时，主会话按照 `audit` 的规则创建不继承产出者
推理的独立、只读 Audit Subagent，以当前需求、实际差异、项目规则和执行证据为依据，至少核验：

- 需求是否完整实现，所有修改是否服务本次需求；
- 存量代码或存量行为的修改是否必要，是否存在影响更小的实现；
- 是否混入无关重构、格式化、依赖变化、顺手修复、无用代码、重复逻辑或过早抽象；
- 实现是否保持未要求改变的行为，并遵守项目既有分层和职责；
- 测试与其他证据是否匹配当前风险和真实入口。

审计只扩大到本次改动引入、扩大或直接触达的现实风险。无关存量问题可以单独说明，但不自动扩大
修复范围；没有实际触发路径的理论风险、无边界安全扫描和追求完美方案不得阻断足够简单、正确且
符合项目习惯的实现。Audit Subagent 只返回结论和反馈事实；主会话负责判断和修改，再按 `audit`
规定交回复审。一次提交当前候选或补充事实并由 Audit 返回结论计为一轮，初审是第一轮，同一审计
最多三轮；修改后旧结论不再证明当前候选通过，复审只需当前需求、当前差异和更新证据，不建立候选
版本对象。第三轮返回后停止 Agent 间交互，能够确认的问题由主会话处理，仍有实质分歧、证据缺口或
风险时如实交给用户。具体创建 Prompt 和复审方法归 `audit` Skill。

## 七、知识沉淀与演进边界

- 项目知识由知识系统独立维护。`know` 从任务过程产物、稳定结果和可回查事实中提取长期有效内容，
  按业务画像、运行模型、功能和数据源分别组织；它不把过程产物本身当作知识内容，也不负责 Harness
  演进。Build 与 Know 沉淀按各自指引加载只读依赖 `rules-know`，共享结构、质量与维护规则；
  它不接管调用方执行，也不是 HARNESS 或 Router 单独安排的节点。Know 检索只读项目知识入口和
  相关内容，不加载该规则依赖。
- `build` 是用户按需启动的首次或结构性知识建设能力，不是 Harness 启用门禁。没有知识库不阻断正常
  任务，也不阻断任务完成后的首次最小知识沉淀。Build 始终先向用户索要或确认信息源，通过问答补齐
  理解；仅在其他来源不足且用户同意时，才局部读代码兜底，不因项目已有代码就默认扫描。
- 项目知识沉淀和 Harness 演进属于不同控制面。`retro` 是投影到业务项目的演进能力，只复盘 Harness 自身机制并提供明确答案。
  复盘在独立新会话中启动，支持用户在新会话主动调用，或由审计完成/任务交付后 AI 提议并在用户确认后拉起新会话注入 Prompt（携带会话 ID、任务目录及产物路径）；
  两会话彻底解耦。Retro 读取任务产物与事件轨迹，在任务目录下产出 `retro.md`，不仅分析问题，还必须以最小代价给出优化 Skill、调整编排、新建能力或增加机制的具体方案，
  严守系统架构分层以防系统腐化；用户拍板后在当前新会话中完成迭代修改与验证，Release、发布和回退不由 Retro 自动执行。
