# 系统演进闭环

> 状态：初步实现，未启用，尚未经过真实任务验证。

## 一、项目知识演进

```text
最终稳定产物 + 交付结果 + 事实来源
→ know 判断是否存在持久变化
├── 无持久变化 → 记录不沉淀
└── 有持久变化 → 形成知识候选
    → audit 知识审计
    → 必要人工批准
    → know 受控写入、更新索引并验证
```

交付系统只触发知识回馈；`audit` 只提供门禁；知识是否记录、归属哪个信息源以及如何写入均由
`know` 决定。历史过程、临时方案和仅服务当前任务的事实不进入长期知识。

## 二、项目知识建设

```text
项目接入要求或用户明确调用 build
→ build 选择业务知识 / 项目运行模型 / 功能知识 / 数据知识子能力
→ 命中的子能力各自形成知识候选
→ 各候选分别经过 audit 与必要人工批准
→ 对应子能力各自应用并验证
→ build 汇总各子能力状态与产物位置
→ 结束
```

`build` 是独立的显式功能，不进入业务任务流程，也不由 `know`、`router` 或知识缺口自动
触发。首次接入分别执行四个子能力；用户再次调用时按其指定范围选择。四个子能力没有共同建设
流程或前后依赖，分别维护自己的来源、结构、方法和验收规则。

## 三、Harness 演进

```text
任务运行证据 / 用户反馈 / 审计问题 / 环境变化
→ retro 复盘或直接形成改进候选
→ 人工决定
├── 不采纳 → 结束
└── 采纳 → 确认 Harness 维护范围、验收、授权和回退方式
    → skill-creator / skill-neat / 其他实现能力
    → 独立审计与效果验证
    ├── 通过 → 人工确认应用 → 演进记录
    └── 不通过 → 回退或继续维护
```

`retro` 只分析和提出候选。获批改进是 Harness 控制面内的维护任务，不进入业务项目的
`intent`、`know` 或 `router`。新建 Skill 使用 `skill-creator`，已有 Skill 迭代使用
`skill-neat`，其他类型产物由对应实现能力处理；改进必须经过人工批准、与影响匹配的审计和验证，并保留回退边界。
