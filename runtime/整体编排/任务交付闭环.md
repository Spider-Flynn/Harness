# 任务交付闭环

> 状态：初步实现，未启用，尚未经过真实任务验证。

## 一、正常主链

```text
用户请求
→ intent
→ know 整合任务信息
→ router
→ 选定执行流程
→ audit
→ cr 组织人工 Review
→ 人工批准并完成获授权交付
→ 系统演进闭环
```

固定门禁是意图确认、任务信息整合、流程路由、独立审计和人工交付。执行流程根据任务选择，不把
所有 Skill 串成固定长链。

## 二、执行流程

可选执行流程、适用条件、Skill 顺序和主要输出只在
[`flows/流程路由.md`](../../flows/流程路由.md)维护。runtime 接收 `router` 选择的一个完整流程，
检查其上游输入仍然有效，按流程推进并接收稳定产物、候选代码、执行证据或反馈请求；不在本
文件复制或改写流程定义。

## 三、回流

| 事件 | 返回位置 | 恢复条件 |
|---|---|---|
| 目标、范围、验收或授权变化 | `intent` | 新意图确认，受影响下游产物失效 |
| 信息源缺失、过期、冲突或无权 | `know` | 用户补充、来源恢复或现有知识修正后重新整合；不自动触发 `build` |
| 当前执行流程不适用 | `router` | 携带仍有效意图、任务信息集合、产物和问题重新选路 |
| 审计不通过或证据不足 | `router` | 根据审计反馈完成修正并重新审计 |
| 人工反馈需要改变候选、验收或证据 | `router` | `cr` 形成反馈请求；runtime 交给 `router` 选择修正流程 |
| 人工直接修改 | `audit` | 记录变化和影响；受影响范围重新审计 |
| 非阻断增量 | 后续任务 | 不改变当前任务范围和交付状态 |

问题根因未知、已有可信根因或需求规则变化时，runtime 只把问题和仍有效输入交给 `router`
或 `intent`；具体选择依据仍以流程路由文件为准，不能把新需求伪装成缺陷。

人工理解性疑问先由 `cr` 依据当前审查包解释并继续 Review；只有需要新增调查、验证或修改时才
形成反馈请求。`cr` 返回人工修改事实后，由 runtime 判断受影响产物与审计结论失效范围。

如果用户目标只要求诊断，`debug` 的根因结论本身作为交付候选进入 `audit → cr`；如果用户目标
包含修复，`debug` 先形成反馈请求返回 `router`，选择 `fix` 后再以修复候选进入正式审计。

## 四、交付

`cr` 组织已确认意图、选定流程、有效稳定产物、事实来源、候选差异、执行证据、审计报告、
已知风险和计划外部操作。人决定是否接受结果、风险和外部操作。

Commit、Push、PR、提测、部署、发布和数据写入只有获得明确授权后才能执行，并以实际工具结果
形成交付回执；审计通过不等于已经交付。
