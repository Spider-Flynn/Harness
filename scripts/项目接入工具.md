# 项目接入工具

> 状态：初步实现，只在临时目录试用过命令，尚未接入真实业务项目。

入口为 `scripts/harness.py`：

```bash
python3 scripts/harness.py init --project <业务项目>
python3 scripts/harness.py doctor --project <业务项目>
python3 scripts/harness.py update --project <业务项目>
python3 scripts/harness.py remove --project <业务项目>
```

| 子命令 | 已实现行为 |
|---|---|
| `init` | 预检同名 Skill 和 `.harness/` 冲突，复制 runtime/flows 入口，建立受管清单和 `.agents/skills/<skill>` 软链接；重复执行只检查现状；首次接入后提示启用前必须显式运行 `build` |
| `doctor` | 只读检查受管文件摘要、Skill 链接目标、源码变化和项目 Git 边界 |
| `update` | 仅在受管内容未被业务项目修改时刷新入口和 Skill 投影，增删目标 Skill |
| `remove` | 仅在受管内容未被修改时移除清单记录的入口和链接，保留业务规则、项目知识与普通 Skill |

工具不会修改业务项目 `AGENTS.md`。接入成功后，使用者仍需在业务项目规则中明确：
“软件开发任务先读取 `.harness/runtime/HARNESS.md`”。这让业务规则继续由业务项目维护，
Harness 只提供受管运行入口。

接入命令只建立物理入口，不能代替 Agent 执行 Skill。首次正常使用 Harness 前，运行时必须按
入口要求显式加载 `build`，完成当前项目知识体系建设；后续不因日常知识缺口自动再次运行。

受管内容被用户修改、清单路径被篡改、同名 Skill 已存在、目标过于宽泛或入口目录不属于工具
时，命令停止，不覆盖普通文件。真实项目 Skill 发现、并发修改和完整任务链仍需在实际接入时
观察。
